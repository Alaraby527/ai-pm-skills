# Skill 创建器

创建一个**从一开始就可调用、可执行、可验证、可发布**的 Skill。不要先写出一个“能看”的版本，再依赖审核去补齐触发、输入、输出和异常处理；质量要求必须在需求澄清和方案设计阶段就成为硬约束。

## 职责边界

本 Skill 只负责创建或重构一个 Skill 的设计与文件内容，包括必要的 supporting resources 规划。它不负责：

- 对一批已有 Skill 做独立评分或横向排名；这属于 `skill-quality-checker`。
- 替用户扩大业务范围、替换目标工具或擅自执行外部发布操作。
- 把多个无关能力塞进一个 Skill；发现职责无法收敛时，应拆分并说明拆分方案。

## 触发与路由

### 应触发

- “帮我创建/新建一个 Skill”
- “设计一个 Skill，让它能……”
- “重构这个 Skill，使它更可调用/更稳定”
- “给我一个 Skill 模板/开发 Skill”
- “把这个工作流封装成 Skill”

### 不应触发

- 只想检查、评分、审计已有 Skill：使用 `skill-quality-checker`。
- 只想安装、下载或启用 Skill：使用 `skill-installer`，并按需做安装前安全审计。
- 只想把一个已完成 Skill 打包或上传：执行对应的打包/发布操作，不重新设计 Skill。

若用户同时提出创建和审计，先按本 Skill 创建，通过创建门槛后再单独进行审计；不能用“审计会发现问题”替代创建阶段的质量设计。

## 创建前质量合同（必须先完成）

在写最终 `SKILL.md` 前，先形成以下合同。任何一项不能回答时，先追问；若用户允许基于假设继续，必须把假设标注为待验证，不能伪造事实。

| 合同项 | 必须明确的内容 | 对应质量要求 |
|---|---|---|
| 核心职责 | 一句话说明只解决哪个任务 | D6 单一职责 |
| 适用/不适用 | 典型请求、边界请求、相邻 Skill 的路由 | D1、D6 |
| 触发条件 | 自然语言触发词、能力描述、排除项 | D1 可调用性 |
| 输入契约 | 必填/选填信息、允许格式、缺失时追问方式 | D2 输入规范 |
| 输出契约 | 最终交付物、结构、格式、完成标准 | D3 输出规范 |
| 方法论依据 | 来源、核心概念、适用前提、不可改写的关键步骤 | D7 方法论还原度 |
| 执行工作流 | 有顺序的步骤、每步动作与产出、决策点 | D5 工作流完整性 |
| 异常与风险 | 不适用、信息不足、冲突、工具失败、敏感风险的处理 | D4 异常兜底 |
| 文件结构 | `SKILL.md`、references、scripts、assets 的必要性 | D8 规范符合度 |

### P0 阻断条件

以下任一项存在，禁止生成“最终版” `SKILL.md`，只能输出阻断项和需要补充的信息：

- 没有可识别的触发条件
- 没有可执行工作流
- 没有明确输出定义
- 一个 Skill 混入三个或更多无关职责，且无法收敛
- 方法论核心概念、步骤或来源不明，或已被错误改写
- 需要依赖数据/来源但用户未提供，且草案会把假设写成事实

## 标准创建流程

严格按顺序执行。每一阶段都要产生可检查的结果；未通过当前阶段，不进入下一阶段。

### 1. 定义任务与边界

写出：

- **一句话职责**：`为 [目标用户] 在 [场景] 完成 [单一任务]`。
- **适用场景**：至少一个真实请求和一个典型输入。
- **不适用场景**：至少一个容易误触发的相邻请求，并指定路由去向。
- **不做什么**：列出不应偷偷扩展的职责。

检查：如果一句话中出现多个并列的核心动词，先拆 Skill 或确认它们确实属于同一闭环。

### 2. 设计可调用性与冲突路由

先写 frontmatter 的 `name` 和 `description` 草案，再检查：

- description 是否同时说清“做什么”和“什么时候用”；
- 触发词是否来自用户真实表达，而不是只有内部术语；
- 是否排除了最容易冲突的 Skill；
- 名称使用小写字母、数字和连字符，且目录名与 `name` 一致。

不要把完整方法论、长清单和所有案例塞进 description；description 只承担发现和路由。

### 3. 定义输入/输出契约

先定义契约，再设计正文，避免生成后才发现“用户不知道要提供什么”或“结果无法验收”。

**输入契约至少包括：**

- 必填信息及其格式；
- 选填信息及缺失时的默认策略；
- 不完整、矛盾、不可验证输入的追问或降级方式；
- 不允许猜测的字段。

**输出契约至少包括：**

- 输出物名称与用途；
- 固定结构或字段；
- 证据、假设、待验证项的标注方式；
- 完成标准和不应声称的结果。

### 4. 还原方法论为可执行工作流

把方法论转成“动作 → 判断 → 产出”的步骤，而不是只罗列概念。每一步必须回答：

1. 读取或收集什么输入？
2. 执行什么具体动作？
3. 使用什么判断规则或方法？
4. 形成什么中间产出？
5. 什么条件下停止、回退或进入下一步？

如果引用外部方法论：保留原始定义、步骤顺序、适用前提和限制；未拿到原文时标注“无法核对”，不要凭记忆补全或改写成貌似权威的结论。

### 5. 设计异常、风险与降级路径

为每类异常写清“识别信号 → 处理动作 → 用户可见结果”：

| 异常 | 必须定义的处理 |
|---|---|
| 必填输入缺失 | 追问哪些字段；无法补齐时输出什么最小结果 |
| 输入相互矛盾 | 告知冲突，列出待确认项；不得擅自选一个 |
| 数据/来源缺失 | 标注假设或无法评估；不得编造数据、用户反馈或引用 |
| 工具或外部资源失败 | 重试边界、降级方案、失败说明和停止条件 |
| 请求不在职责内 | 明确拒绝越界部分，建议正确 Skill 或下一步 |
| 高风险/敏感场景 | 限制结论范围，要求人工确认或转交适当流程 |
| 结果无法满足完成标准 | 输出缺口和补证据清单，不伪装为已完成 |

### 6. 规划渐进式披露与 supporting resources

`SKILL.md` 保留触发、边界、核心工作流、质量门槛和必要异常处理；只有在实际需要时才增加 `references/`、`scripts/` 或 `assets/`。

- 需要反复查阅的长模板、领域规范、方法论原文放入 `references/`；
- 需要确定性重复执行的逻辑才放入 `scripts/`；
- 生成结果需要固定素材时才放入 `assets/`；
- 每个 supporting resource 必须在 `SKILL.md` 中说明用途和读取时机；
- 删除未被引用、没有实际用途的占位文件。

### 7. 编写并验证测试案例

在生成最终版前，用同一份设计合同构造至少三类测试，不要只测试理想请求：

- **正例**：完整输入，能按工作流得到预期输出；
- **边界例**：缺少可选信息、范围临界或与相邻 Skill 相似的请求；
- **失败例**：缺少必填信息、来源冲突、工具失败或明确越界的请求。

记录每个案例的：触发结果、所需追问、关键步骤、输出结构、异常处理和是否达到完成标准。案例只能使用真实已知信息；示例数据必须明确标记为示例/假设。

### 8. 创建前八维预检

最终文件生成前，按下表逐项评分（0–5 分），并引用草案中的具体章节或句子作为依据：

| 维度 | 权重 | 通过条件 |
|---|---:|---|
| D1 可调用性 | 15% | 触发词、能力和冲突边界清楚 |
| D2 输入规范 | 10% | 必填/选填、格式、缺失处理明确 |
| D3 输出规范 | 10% | 输出物、结构和完成标准可验收 |
| D4 异常兜底 | 15% | 主要异常有识别、处理和降级结果 |
| D5 工作流完整性 | 15% | 步骤可执行，产出递进，有检查点 |
| D6 单一职责 | 10% | 只解决一个核心任务，无无关职责 |
| D7 方法论还原度 | 15% | 核心定义和步骤有来源或明确标注不可评估 |
| D8 规范符合度 | 10% | frontmatter、命名、长度、引用和渐进式披露合规 |

计算加权平均分：`Σ(维度得分 × 权重)`。发布门槛是：**无 P0、每个维度 ≥ 4、加权平均 ≥ 4.5**。任何未达标项都必须回到对应设计阶段修订，而不是在报告中掩盖。

## 最终输出契约

只有通过创建前预检后，才输出最终版。默认交付以下内容：

1. `skills/<name>/SKILL.md`：可直接加载的 Skill 文件；
2. supporting resources 规划：列出实际创建的文件、用途和读取时机；
3. 触发词与冲突 Skill 分析；
4. 输入/输出契约；
5. 正例、边界例、失败例测试记录；
6. D1–D8 预检评分表（每项证据、得分和遗留风险）；
7. 未解决问题与发布阻断项（必须明确写“无”或列出 P0/P1/P2）。

若未通过：不要把未通过的内容命名为最终版或写入发布目录。可以输出设计草案、缺口、待用户确认的问题和下一轮修订建议。

## 发布前后边界

创建前预检是生成门槛，不等同于事后审计。通过后仍可按用户要求使用 `skill-quality-checker` 做独立复核；复核发现问题时，回到对应设计阶段修订并重新跑三类测试和预检。任何修改触发条件、输入输出或工作流的提交，都必须做回归验证。
