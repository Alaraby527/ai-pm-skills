# 完整案例：AI 评测自迭代工作台

> 这是一个真实的 Vibe Coding 项目完整案例，展示如何用六阶段方法论从零到一完成一个 AI 产品。
> 项目：AI 评测自迭代工作台 —— 自动抓取 AI 客服对话、大模型批量评测、Badcase 归因、生成 QA 草稿。

---

## 项目背景

**目标用户**：负责 AI 产品质量的产品经理或运营团队（如电商客服团队负责人）。

**核心痛点**：
- AI 客服上线后，每天产生成千上万条对话
- 人工一天只能抽检约 100 条，覆盖率不到 2%
- 人工抽检只能判断"好或不好"，说不清是知识库缺信息、AI 理解错意图、还是回答敷衍
- 不同原因对应不同改进方法，原因说不清就无法转化为行动

**已知约束**：
- 一个人维护
- 单台服务器运行
- 每日处理量小于 1 万条
- 第一版优先验证核心链路，不追求大规模和多租户

---

## 六阶段推进记录

### 第一阶段：需求对齐

**关键决策**：
1. 区分两条链路 —— 质量告警（可自动）vs 改进产物（必须人工审核）
2. QA 草稿状态固定为 draft → approved → exported，第一版不允许自动写入知识库
3. 产出正式 PRD 文档，作为后续所有开发的事实源

**产出物**：
- PRD 文档（13 个章节：项目定位、核心闭环、范围与不做、数据采集、评测引擎、看板预警、Badcase 归因、QA 草稿与人工审核、一键流水线、前端页面、演示数据、测试验收、风险边界）

---

### 第二阶段：方案输出

**关键决策**：
1. 驳回了 AI 第一版方案中使用 PostgreSQL、Docker Compose、Recharts 的设计 —— 与已确认的 SQLite + 本地单机方案不一致
2. 用七层清单逐项检查方案完整性
3. 提前写死 AGENTS.md：技术栈锁定、15 张表名、跨阶段字段、枚举、状态、端口、路由

**技术栈最终确定**：
- 后端：FastAPI + SQLAlchemy + SQLite + Alembic + APScheduler + LiteLLM
- 前端：Next.js App Router + TypeScript + shadcn/ui + ECharts
- 部署：本地单用户，127.0.0.1，单个 Uvicorn worker

**产出物**：
- 七层完整方案（数据层 / 评测层 / 执行层 / 异常层 / 展示层 / 改进产物层 / 风险层）
- AGENTS.md 项目规则文件
- 文件级实施计划

---

### 第三阶段：MVP 开发（分 5 个 Phase）

| Phase | 模块 | 关键产出 | 测试数 |
|---|---|---|---|
| Phase 1 | 数据采集 | HTTP JSON 数据源接入、字段映射、采样、入库、页面展示 | 56 项后端测试 |
| Phase 2 | 评测引擎 | 模型配置、批量评测、单条结果、Prompt 模板、运行详情页 | 三类模型输出全部 mock 验证 |
| Phase 3 | 看板与预警 | 质量指标看板、阈值告警、飞书通知 | - |
| Phase 4 | Badcase 归因与 QA | 归因分类、missing_data 生成 QA 草稿、人工批准、导出 | 3 条 Badcase 完整归因 |
| 一键流水线 | 五阶段编排 | collecting → evaluating → alert_scanning → analyzing → generating_qa → completed | 复用已有 Service，不复制业务逻辑 |

**开发方式**：
- TDD：RED → GREEN → REFACTOR
- 每轮独立工作区（git worktree）
- 三层验收：状态层 + 内容层 + 页面链路层
- 每完成一个阶段单独 Git commit，不擅自合并

---

### 第四阶段：项目测试

**只读冒烟结果**：
- 10 个固定前端路由中只有 5 个正常（另外 5 个 404）
- 6 个只读后端 API 全部正常
- 看板可以打开但运行数据库为空

**测试数据源搭建**：
- 本地 HTTP mock 服务，持续运行
- 正常接口：100 条有效记录
- 异常接口：100 条有效记录 + 5 条映射异常
- 整次失败接口：缺少 data.items 路径

**真实模型验证发现的问题**：
- QA 草稿中出现了无法从现有事实依据验证的政策内容（编造）
- 决策：全部不批准、不导出，保持 draft 状态
- 原则：技术调用成功 ≠ 内容可以发布

---

### 第五阶段：Bug 改进

**发现的问题与根因**：

| 现象 | 根因 | 修复方式 |
|---|---|---|
| 5 个前端路由 404 | 当前运行的 main 较旧，后续功能在未合入分支 | 把已完成并验证的线性分支合入 main |
| 看板空数据 | 运行服务用 workbench.sqlite3，测试种子数据写入另一份 Demo 数据库 | 统一数据库路径，隔离测试和正式库 |
| 前端依赖不完整 | 借用了其他项目的 node_modules | 恢复本项目自己的依赖和 lockfile |
| 首页下拉框为空 | 后端连接了空的默认数据库 | 切换到正确的运行数据库 |

**回归验证**：
- 10 个固定路由全部正常
- 7 个 E2E 用例全部通过
- 后端 108 项测试通过
- 正式工作数据库没有被测试数据污染

---

### 第六阶段：最终交付

**最终状态**：
- 用户从首页选择数据源和评测任务，点击启动
- 系统依次完成：采集 → 评测 → 预警扫描 → Badcase 归因 → QA 草稿生成
- 前端演示结果：输入 105 条，成功采集 100 条，映射失败 5 条，评测成功 100/100，Badcase 31 条，QA 草稿 9 条，已批准 0，已导出 0，通过率 69%，平均分 3.46
- 人工边界完整：QA 是否正确、是否批准、是否导出，仍由人决定

---

## 这个案例的关键经验

1. **需求阶段不急着写代码**：先花时间划清边界，区分"自动"和"人工"两条链路
2. **方案必须对照需求**：AI 给出的"专业方案"可能偏离你确认的约束，必须主动驳回
3. **AGENTS.md 提前写死规则**：防止开发中字段名、状态、技术栈漂移
4. **分模块开发，每模块独立验收**：不要一次把所有功能写完再测试
5. **三层验收不能省**：只看测试通过或接口 200 是不够的
6. **冒烟测试只记录不修复**：先记录问题现象，再系统化诊断根因
7. **技术成功 ≠ 内容可用**：AI 生成的 QA 草稿必须人工审核，编造的内容不能自动发布
8. **修复后沿原路径回归**：不要换一条"能跑通"的路径就算通过

## 你可以怎么复用这个案例

- 如果你要做的也是"AI 自动处理 + 人工审核"类产品，直接参考它的两条链路划分方式
- 如果你的项目也需要分阶段开发，参考它的 Phase 拆分粒度（每个 Phase 有独立测试和验收）
- 如果你担心 AI 写代码跑偏，参考它的 AGENTS.md 规则锁定和七层方案检查
- 如果你需要测试，参考它的三层验收方法和 mock 数据源搭建
