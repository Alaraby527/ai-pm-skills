# Vibe Coding 六阶段 Prompt 模板合集

> 以下模板按六阶段顺序排列，共 23 个节点。每个模板都可以直接复制使用，把 `【】` 中的占位符替换成你的项目实际内容即可。
>
> **核心原则**：关键边界没有确认之前，不要写代码。

---

## 第一阶段：需求对齐（3 个节点）

### 01｜锁定需求起点

**用途**：项目还没进入方案设计时，先把目标用户、真实场景、核心问题和 AI 的任务放到同一份描述里。

```plain text
我要做一个「【项目名称】」。

【谁】
【目标用户角色，例如：负责 AI 产品质量的产品经理或运营团队】
例如：【一个具体的用户画像例子】

【场景】
【真实业务场景描述，例如：AI 客服上线后，每天产生成千上万条对话】
【当前痛点的量化数据，例如：人工一天只能抽检约 100 条，覆盖率不到 2%】

【问题】
人工/现有方案只能判断【好或不好】，但很难进一步说明：
1. 【原因类别一】；
2. 【原因类别二】；
3. 【原因类别三】。

不同原因对应不同改进方法。如果原因说不清，结果就无法转化为行动。

【希望 AI 帮我完成的事情】
1. 【自动化能力一】；
2. 【自动化能力二】；
3. 【自动化能力三】；
4. 【自动化能力四】；
5. 【自动化能力五】；
6. 【人工审核/确认环节，明确不能自动做什么】。

【已知约束】
1. 【资源约束一，例如：一个人维护】；
2. 【资源约束二，例如：单台服务器运行】；
3. 【规模约束，例如：每日处理量小于 1 万条】；
4. 【版本约束，例如：第一版优先验证核心链路，不追求大规模和多租户】。

【你现在要做什么】
请使用 brainstorming 方法，并进入 Plan 模式。
先复述你对需求的理解，再主动向我提问。
在关键边界没有确认之前，不要写代码，也不要自行补需求。

请优先确认：
- 第一版的数据来源；
- 采样/处理方式；
- 【核心规则/标准】；
- 【异常案例的判断规则】；
- 【分类/归因规则】；
- 自动化边界；
- 人工审核边界；
- 通知/预警方式；
- 第一版明确不做什么。
```

---

### 02｜划清自动化边界

**用途**：目标清楚后，区分"可以自动做的"和"必须人工决定的"两条链路，防止 AI 越过人工审核。

```plain text
基于前面的讨论，请重新整理第一版边界。

请特别区分下面两条链路，不要混在一起：

【链路 A：【自动链路名称，如质量告警】】
当【指标一】、【指标二】或【异常率】达到规则阈值时，
允许自动向【通知渠道，如飞书】发送【告警/通知】。

【链路 B：【人工链路名称，如改进产物】】
【触发条件，如 Badcase 归因】后，只有【符合条件的类别】可以生成【产物，如 QA 草稿】。
【产物】只允许进入：
draft → approved → exported

其中：
- draft 必须人工审核；
- 未批准不能导出；
- 第一版不允许自动写入【下游系统】；
- 第一版不允许自动推送【产物】；
- 不增加 pushed 状态；
- 导出就是本链路终态。

请输出：
1. 已确认的需求；
2. 已确认的第一版边界；
3. 仍然存在的冲突或歧义；
4. 需要我继续确认的问题。

没有确认的内容，请明确标记"待确认"，不要根据常见做法自行补齐。
```

---

### 03｜建立需求事实源

**用途**：把口头共识变成稳定文档，让后续的方案、开发和验收都引用同一份事实。

```plain text
需求已经完成对齐。

请把当前确认内容整理成一份可用于设计、开发和验收的正式需求文档，
保存到：
docs/requirements/【项目名】-prd.md

【文档必须包含】
1. 项目定位、目标用户和核心问题；
2. 第一版核心闭环；
3. 第一版范围与明确不做的内容；
4. 【模块一，如数据采集】；
5. 【模块二，如评测引擎】；
6. 【模块三，如看板与预警】；
7. 【模块四，如 Badcase 归因】；
8. 【模块五，如 QA 草稿、人工审核与导出】；
9. 【模块六，如一-键流水线】；
10. 【模块七，如前端页面】；
11. 【模块八，如演示数据】；
12. 测试与验收；
13. 风险与安全边界。

【处理规则】
- 以最新确认内容为准；
- 旧方案与最新需求冲突时，覆盖旧方案；
- 原材料里出现缺失表格或"暂时无法展示"的位置，要指出缺口；
- 能从已确认上下文确定的内容，可以补成完整规格；
- 无法确定的内容必须标记"待确认"，不要硬凑；
- 不得保留 TODO、TBD 或无法执行的占位说明；
- 不要开始写代码。

完成后请汇报：
1. 文件路径；
2. 文档章节；
3. 补齐了哪些缺口；
4. 解决了哪些冲突；
5. 还剩哪些待确认项。
```

## 第二阶段：方案输出（4 个节点）

### 04｜驳回偏离约束的方案

**用途**：AI 的第一版方案可能"听起来专业"但偏离了已确认的约束，必须要求 AI 对照需求修订。

```plain text
你刚才输出的方案暂不批准。

请先对照下面两组内容，检查方案是否偏离了已经确认的项目约束。

【你当前方案中的内容】
- 【方案中偏离的技术一】；
- 【方案中偏离的技术二】；
- 【方案中偏离的技术三】；
- 【方案中偏离的设计一】；
- 【方案中偏离的设计二】；
- 第一版不包含【已确认必须包含的模块】。

【当前权威需求】
- 【技术栈一，如 FastAPI + SQLAlchemy + SQLite + Alembic】；
- 【技术栈二，如 APScheduler】；
- 【技术栈三，如 LiteLLM，所有模型调用统一经过 llm_client.py】；
- 【技术栈四，如 Next.js App Router + TypeScript + shadcn/ui + ECharts】；
- 【业务模块一，如飞书质量告警】；
- 【业务模块二，如第一版核心闭环包含 QA 草稿、人工审核和导出】；
- 【部署约束，如本地单用户运行，默认只监听 127.0.0.1】；
- 【运行约束，如单个 Uvicorn worker】。

请输出：
1. 两版方案的差异；
2. 哪些内容必须删除；
3. 哪些内容必须替换；
4. 修订后的总体架构；
5. 仍然存在的需求缺口。

旧方案与最新需求冲突时，以最新需求为准。
不要为旧方案辩护，也不要保留两套实现。
这一轮只修订方案，不要写代码。
```

### 05｜检查方案完整性（七层清单）

**用途**：用七层清单逐项查缺口，确保方案不只覆盖正常流程，也覆盖执行、异常、展示和风险。

```plain text
基于已经确认的需求，请输出第一版完整方案。

先不要写代码。

我会按下面七层检查你的方案。
请逐层回答，不能跳过：

【1. 数据层】
- 数据源如何接入；
- 第一版处理多少条；
- 字段映射规则是什么；
- 映射失败如何记录；
- 采样和数量上限按什么顺序执行。

【2. 【核心业务层，如评测层】】
- 【核心标准】由谁确定；
- Prompt 必须包含哪些输入；
- 模型输出固定哪些字段；
- 如何判断 pass / 通过；
- Badcase / 异常案例如何产生。

【3. 执行层】
- 并发策略；
- 失败重试；
- 单条失败是否影响整批；
- 运行状态如何持久化；
- 前端如何查看进度。

【4. 异常层】
- 【常见异常一，如 Markdown 包裹的 JSON】如何处理；
- 完全无法解析时如何处理；
- schema 不合法时如何处理；
- 链路异常是否进入质量指标。

【5. 展示层】
- 看板显示哪些指标；
- 时间范围如何选择；
- 预警使用哪些指标；
- 预警如何触达。

【6. 【改进产物层】】
- 【归因/分类】是否使用固定枚举；
- 哪类 Badcase 可以生成【产物】；
- 【产物】状态如何流转；
- 哪一步必须人工确认。

【7. 风险层】
- 密钥如何保存；
- 哪些内容不能写入数据库、日志或响应；
- 自动化边界在哪里；
- 【部署方式，如 SQLite、调度和单机部署】最容易出现什么问题。

【输出要求】
1. 先给总体架构；
2. 再按七层逐项回答；
3. 每层标记：已覆盖 / 部分覆盖 / 未覆盖；
4. 缺哪层就明确说缺哪层；
5. 不要用合理猜测把缺口填满；
6. 最后单独回答：这个项目最容易翻车的地方是什么？
```

### 06｜固化项目规则（AGENTS.md）

**用途**：把后续 AI 能改什么、不能改什么定死，防止开发中字段和状态漂移。

```plain text
基于已经确认的需求文档和技术选型，生成项目根目录的 AGENTS.md。

这不是建议清单，而是后续所有开发者和 AI Agent 都必须遵守的项目规则。

【必须写入】
1. 技术栈锁定；
2. 禁止擅自引入的同类技术；
3. 项目目录结构；
4. 模块与文件职责；
5. 这类项目最容易犯错的硬性规则，控制在 8 条以内；
6. 一节"不可变约定"；
7. 需求变更时的处理方式；
8. 每个模块的完成与验收标准。

【不可变约定必须提前定死】
- 数据库表名；
- 跨阶段主键和关联字段；
- API 与前端 JSON 的字段命名；
- 数据源类型；
- 固定采集映射键；
- 模型配置分组；
- 裁判/评测输出字段；
- pass 计算规则；
- 归因/分类枚举；
- 所有状态枚举；
- 流水线阶段；
- 前后端端口；
- service、client、job 模块名称；
- 前端固定路由；
- 【产物】导出字段及顺序。

【约束】
- 禁止使用"建议""可以考虑"等软表达；
- 不允许保留两套字段名、两套状态或两条平行业务路径；
- 未经我确认，不得替换技术栈；
- 后续需求若触及不可变约定，必须先更新需求文档和 AGENTS.md；
- 不要写业务代码。

完成后请检查：
- 硬性规则数量；
- 固定表名数量；
- Prompt 必需插槽是否完整；
- 是否存在占位符；
- 是否存在前后矛盾。
```

### 07｜暴露开发歧义

**用途**：规则锁定后，把方案落到文件职责，并暴露会改变实现和测试的歧义。

```plain text
阅读以下内容：
1. 需求文档中的【模块一】章节；
2. 根目录 AGENTS.md；
3. 当前仓库已有文件。

请使用 writing-plans 方法整理文件级实施方案。

这一轮不要写代码。
也不要重新设计已经确定的表、字段和状态。

请只输出两部分：

【第一部分：文件级方案】
- 计划创建或修改哪些文件；
- 每个文件负责什么；
- 每个文件依赖什么；
- 哪些逻辑属于 service；
- 哪些逻辑属于 client；
- 哪些逻辑只能放在路由层；
- 前端通过哪个统一入口调用 API。

【第二部分：需求缺口】
- 文档里是否存在遗漏；
- 是否存在两种以上合理解释；
- 哪些歧义会改变实现结果；
- 哪些歧义会改变测试断言；
- 哪些问题必须由我确认后才能开发。

请按影响程度排序。
没有提到的层，直接说没有提到，不要硬凑。
```

## 第三阶段：MVP 开发范围（6 个节点）

### 08｜划定 MVP 闭环

**用途**：用"能否产出可检查结果"判断 MVP，把大项目拆成可独立验收的轮次。

```plain text
基于已经确认的需求和方案，帮我确定本轮 MVP 开发范围。

【判断标准】
用户【执行操作，如选择数据源和评测任务并启动】后，
系统能否产生一个有价值、可检查的结果？

这个结果至少应该包含：
- 【指标一，如采集到了多少条】；
- 【指标二，如多少条评测成功】；
- 【指标三，如多少条未通过】；
- 【指标四，如 Badcase 的原因是什么】；
- 【指标五，如生成了多少条待人工审核的草稿】。

【请把方案分成两类】
A. 验证核心链路必须有；
B. 不影响核心链路成立，可以后做。

【范围规则】
- 不做多租户；
- 不做大规模分布式任务；
- 不做【自动化推送】；
- 不做【自动写入下游系统】；
- 不做【改进前后自动对比】；
- 不增加第二套数据源、模型客户端或任务系统；
- 不允许一键流水线复制已有模块的业务逻辑。

【拆分要求】
如果核心链路横跨多个模块，请拆成多轮：
- 每轮先确认方案；
- 再写测试；
- 再实现；
- 再完成状态层、内容层和页面链路层验收；
- 一轮完成后再进入下一轮。

请输出：
1. MVP 核心闭环；
2. 本轮范围；
3. 延后范围；
4. 开发轮次；
5. 每轮完成标准；
6. 每轮依赖关系。
```

### 09｜开发第一个模块（TDD 完整模板）

**用途**：第一个模块的完整开发指令，从 TDD 到三层验收。后续每个模块都可以复用这个模板结构。

```markdown
现在正式开始 Phase N：【模块名称】开发。

请按照已经确认的需求文档和技术方案，完成本模块的生产代码、自动化测试和验收。

## 一、开发依据

1. `docs/requirements/【项目名】-prd.md` 中的 M【N】【模块名】规格；
2. 根目录 `AGENTS.md` 中的技术栈、字段、状态和模块约定；
3. 已确认的文件级实施计划。

如果已有实现与最新需求冲突，以 PRD 和 AGENTS.md 为准，不要自行重新设计。

## 二、本轮开发范围

### 1. 【子功能一，如数据源接入】
- 【具体功能点一】；
- 【具体功能点二】；
- 【具体功能点三】；
- 失败时的处理方式；
- 不增加其他类型的【功能扩展】。

### 2. 【子功能二，如数据采集与处理】
- 【处理步骤一】；
- 【处理步骤二】；
- 【标准字段固定为 xxx】；
- 【采样规则】；
- 单条记录失败不能中断整批；
- 失败记录及原因写入错误表。

### 3. 数据持久化与任务管理
- 使用既定 SQLAlchemy Model 和 Alembic Migration；
- 将成功数据写入目标表；
- 保存任务状态、处理数量、成功数量和失败数量；
- 各项统计口径严格遵循 PRD，不能自行修改计算规则；
- 任务执行异常时，必须保留可追踪的错误信息。

### 4. 前后端功能接通
- 实现既定的 API 和任务执行入口；
- 按文件级方案完成唯一的 client 和 service；
- API、job 和页面复用同一套 service，不复制业务逻辑；
- 完成既定页面功能；
- 页面显示的数量和状态必须与后端真实数据一致。

## 三、开发方式

使用以下方法：
- 创建独立开发工作区（git worktree）；
- 测试驱动开发：按照 RED → GREEN → REFACTOR；
- 完成后验证实际结果。

按以下顺序执行：
1. 检查当前仓库和文件级实施计划，确认缺失的生产实现；
2. 编写本模块测试，先运行并验证测试出现预期 RED；
3. 按测试和需求实现最小必要生产代码；
4. 运行测试，修复问题，直到达到 GREEN；
5. 在不改变既定契约的前提下整理代码；
6. 接通 API、数据库、调度任务和前端页面；
7. 执行本模块独立验收；
8. 验收完成后汇报结果，不擅自合并或推送。

### 测试与实现必须覆盖
- 【正常场景一】；
- 【异常场景一，如字段路径未命中】；
- 【异常场景二，如 null 和字段类型错误】；
- 【异常场景三，如单条失败与整次失败的区分】；
- 【核心规则验证，如采样可复现】；
- 【失败记录写入错误表】；
```

## 第六阶段：最终交付（1 个节点）

### 23｜确认交付边界

**用途**：只汇报有证据支持的当前状态，不夸大、不省略。

```plain text
请基于当前已经完成的项目状态，给我一份最终交付摘要。

只汇报可以被证据支持的结果：
- 当前分支和 commit；
- 前后端启动方式；
- 用户从哪个页面开始操作；
- 已实现的核心链路；
- 最后一轮自动化测试结果；
- 最后一轮真实前端运行结果；
- 当前仍保留的人工边界；
- 已知但未纳入本轮的事项。

不要把"测试通过"写成"产品一定没有问题"。
不要把 draft 写成已发布。
不要省略仍未完成或仍需人工判断的部分。
```
