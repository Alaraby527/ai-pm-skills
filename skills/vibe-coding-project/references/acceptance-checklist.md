# 三层验收清单与质量门禁

> Vibe Coding 项目开发中，每个模块完成后必须通过三层验收才能标记为"完成"。
> **核心原则**：测试通过 ≠ 功能完成；接口 200 ≠ 验收通过。

---

## 第一层：状态层（自动化验证）

**目标**：确认代码在技术层面没有阻塞性错误。

| 检查项 | 通过标准 | 不通过怎么办 |
|---|---|---|
| 后端单元测试 | pytest 全部通过，无 FAIL / ERROR | 修复失败的测试，不要删除测试来"让它通过" |
| 前端单元测试 | 全部通过 | 修复失败的测试 |
| 前端生产构建 | `npm run build` 成功，无 TypeScript 错误 | 修复类型错误和构建错误 |
| 数据库迁移 | Alembic 迁移成功，表结构与 AGENTS.md 一致 | 修正迁移脚本 |
| 启动无阻塞错误 | 后端能启动、前端能启动、无控制台报错 | 修复启动错误 |

**常见陷阱**：
- ❌ 为了让测试通过，把测试断言改松（如把"必须有 5 条"改成"至少有 0 条"）
- ❌ 跳过失败的测试（`@pytest.mark.skip`）而不修复
- ❌ 只跑新增的测试，不跑回归测试

---

## 第二层：内容层（数据验证）

**目标**：确认数据真的写进了数据库，统计数字对得上账。

| 检查项 | 通过标准 | 不通过怎么办 |
|---|---|---|
| 真实数据入库 | 直接查询数据库，目标表有真实记录（不是空表） | 检查采集/写入逻辑 |
| 错误记录明细 | 错误表中有对应的失败记录和原因 | 检查异常处理逻辑 |
| 统计数字对账 | 输入总数 = 成功数 + 失败数（字段映射失败） + 整次失败数 | 核对统计口径，确保与 PRD 一致 |
| 状态流转正确 | 草稿状态 = draft，没有自动变成 approved | 检查状态机逻辑 |
| 关键字段完整 | 每条记录的必填字段都有值，没有 NULL | 检查数据映射和校验 |

**验证方法**：
```sql
-- 示例：查询原始数据表
SELECT COUNT(*) FROM raw_conversations;

-- 示例：查询错误表
SELECT * FROM collection_record_errors LIMIT 10;

-- 示例：核对统计
SELECT 
  COUNT(*) AS total,
  SUM(CASE WHEN status = 'succeeded' THEN 1 ELSE 0 END) AS succeeded,
  SUM(CASE WHEN status = 'failed' THEN 1 ELSE 0 END) AS failed
FROM eval_runs;
```

**常见陷阱**：
- ❌ 只看接口返回 200，不查数据库
- ❌ 统计数字对不上账（输入 100 条，成功 100 条，但错误表还有 5 条）
- ❌ 测试数据和生产数据库混在一起

---

## 第三层：页面链路层（真实用户路径验证）

**目标**：从用户真正使用的前端页面走一遍，确认页面显示和数据库一致。

| 检查项 | 通过标准 | 不通过怎么办 |
|---|---|---|
| 页面能打开 | 首页、列表页、详情页等固定路由都能正常渲染 | 检查路由配置和后端服务 |
| 下拉框有选项 | 数据源下拉框、任务下拉框有真实数据 | 检查 API 返回和数据库连接 |
| 能启动任务 | 从首页点击启动按钮，任务能开始执行 | 检查前端事件绑定和后端 API |
| 任务进度可见 | 页面能看到任务状态（运行中/已完成/失败） | 检查 WebSocket 或轮询逻辑 |
| 结果数字一致 | 页面显示的数量 = API 返回的数量 = 数据库记录数 | 检查前端展示逻辑 |
| 人工边界完整 | 页面上没有"自动批准""自动推送"按钮 | 检查前端组件和权限控制 |
| 空状态正确 | 没有数据时显示友好提示，不是白屏或报错 | 检查空状态处理 |

**验证方法**：
1. 从首页 `/` 开始操作（不要直接进入 `/pipeline` 状态页）
2. 选择真实数据源和任务
3. 点击启动
4. 等待任务完成
5. 截图记录页面数字
6. 用 SQL 查询数据库对账
7. 确认 QA 草稿状态仍为 draft

**常见陷阱**：
- ❌ 绕过前端直接调 API 验证（"反正接口是好的"）
- ❌ 页面数字和数据库数字不一致
- ❌ 下拉框是空的，但以为是"还没有数据"，其实是数据库连接错了

## 阶段质量门禁汇总

每阶段必须通过以下门禁才能进入下一阶段：

| 阶段 | 门禁项 | 不通过时 |
|---|---|---|
| 需求对齐 | PRD 完整 + 所有关键边界已确认 + 无 TODO/TBD | 继续追问，直到边界清晰 |
| 方案输出 | 七层方案无"未覆盖" + AGENTS.md 无占位符 + 文件级方案无歧义 | 补缺口，歧义项用户确认 |
| MVP 开发 | 三层验收全部通过（状态 + 内容 + 页面链路） | 回到对应模块修复 |
| 项目测试 | 冒烟测试报告完整 + 真实入口 E2E 通过 | 记录问题，进入 Bug 改进 |
| Bug 改进 | 原路径回归通过 + 核心 E2E 无回归 + 人工边界未破坏 | 重新诊断根因 |
| 最终交付 | 所有结论有证据支撑 + 无夸大 + 无遗漏人工边界 | 补证据，修正表述 |

---

## 人工边界检查清单（不可越过）

以下操作在第一版中必须保持人工确认，AI 不得自动执行：

- [ ] QA / 改进草稿的**批准**操作
- [ ] QA / 改进草稿的**导出**操作
- [ ] QA / 改进草稿的**对外推送**操作
- [ ] 知识库的**自动写入**操作
- [ ] 生产环境的**部署**操作
- [ ] 费用 / 配额的**超限**操作

**验证方法**：
- 页面上不应该有"一键批准""一键导出""自动推送"等按钮
- 数据库中 approved / exported 数量应为 0（除非人工操作过）
- 日志中不应该有自动批准的记录

---

## 证据保留要求

每次验收都必须保留以下证据，用于最终交付和回溯：

1. **测试结果**：pytest 输出、build 输出截图
2. **数据库记录**：关键表的行数和样例数据
3. **页面截图**：首页、任务列表、详情页、结果页
4. **Git 记录**：当前分支、commit hash、工作树状态
5. **运行环境**：后端端口、前端端口、数据库路径

**核心原则**：不要用"应该好了""已经覆盖"代替证据。
