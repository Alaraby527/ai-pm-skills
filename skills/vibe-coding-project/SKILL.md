# Vibe Coding 项目推进方法论

## 简介

**干什么的**：教你用结构化 Prompt 驱动 AI（如 Cursor / Claude Code / Devin）从零到一完成一个真实软件项目，避免"AI 写了一堆但项目跑偏、无法验收、bug 满天飞"的常见问题。

**核心方法论**：六阶段推进法 —— 需求对齐 → 方案输出 → MVP 开发 → 项目测试 → Bug 改进 → 最终交付。每一阶段有明确的 Prompt 模板、产出物和验收门槛，不通过当前阶段不进入下一阶段。

**你能得到什么**：
- 一份可直接复制的六阶段 Prompt 模板合集（references/prompts.md）
- 三层验收清单（状态层 / 内容层 / 页面链路层）
- 完整实战案例（AI 评测自迭代工作台，23 个真实对话节点）

**文件结构**：
```
vibe-coding-project/
├── SKILL.md                              # 主文档：触发条件 + 六阶段工作流 + 质量红线
└── references/
    ├── prompts.md                         # 六阶段完整 Prompt 模板合集（23 个节点）
    ├── acceptance-checklist.md            # 三层验收清单与质量门禁
    └── case-example.md                    # 完整案例：AI 评测自迭代工作台
```

## 触发场景

当用户需要用 AI 驱动开发方式（Vibe Coding）推进一个真实软件项目时触发。典型场景包括：
- "我想用 AI 做一个 XX 项目，怎么开始？"
- "Vibe Coding 怎么避免跑偏？"
- "怎么用 Prompt 带 AI 把一个项目做完？"
- "AI 写代码总是写着写着就偏了，怎么办？"
- "有没有一套 AI 开发项目的方法论？"

## 输入要求

**必需信息**：
- 项目想法 / 目标产品的一句话描述
- 目标用户是谁、解决什么核心问题

**可选补充信息**：
- 技术栈偏好（如 Python / React / 本地部署 / 云端）
- 资源约束（单人维护 / 服务器配置 / 日处理量上限）
- 第一版明确不做的内容
- 已有的 PRD / 需求文档

**信息不全时的追问话术**：
- 缺目标用户："这个工具主要给谁用？他们在什么场景下会用到？能举一个真实的痛点例子吗？"
- 缺约束："第一版你最关心的边界是什么？比如单机还是分布式？要不要多用户？每日大概处理多少数据？"
- 缺"不做什么"："这个项目第一版你明确不想做哪些功能？划清边界比列需求更重要。"

## 六阶段工作流

### 第一阶段：需求对齐（不要急着写代码）

**目标**：把目标用户、真实场景、核心问题和 AI 的任务放到同一份描述里，建立需求事实源。

**关键动作**：
1. **锁定需求起点**：用结构化 Prompt 一次性说清【谁】【场景】【问题】【希望 AI 做什么】【已知约束】【现在要做什么】
2. **划清自动化边界**：区分"可以自动做的"和"必须人工决定的"两条链路，防止 AI 越过人工审核
3. **建立 PRD 事实源**：把口头共识写成正式需求文档（PRD），后续所有设计和开发都引用同一份

**产出物**：
- 一份完整的 PRD 文档（含项目定位、核心闭环、范围与不做清单、数据采集、评测引擎、看板预警、Badcase 归因、QA 草稿与人工审核、测试验收、风险边界）

**质量红线**：
- 关键边界没有确认前，禁止写代码
- 未确认的内容必须标记"待确认"，不得根据常见做法自行补齐
- 不得保留 TODO / TBD 占位说明

### 第二阶段：方案输出（先方案后代码）

**目标**：AI 输出的方案必须对照已确认的需求文档，不能"听起来专业就直接接受"。

**关键动作**：
1. **驳回偏离约束的方案**：如果 AI 用了 PRD 里没确认的技术栈（如 PRD 写了 SQLite，AI 却用 PostgreSQL），必须要求 AI 对照需求修订，不为旧方案辩护
2. **七层方案完整性检查**：逐层检查数据层 / 评测层 / 执行层 / 异常层 / 展示层 / 改进产物层 / 风险层，每层标记"已覆盖 / 部分覆盖 / 未覆盖"
3. **固化 AGENTS.md 项目规则**：把技术栈、目录结构、字段命名、状态枚举、端口路由等"不可变约定"提前写死，防止开发中漂移
4. **暴露开发歧义**：列出文件级实施方案，同时指出哪些地方存在两种以上合理解释，需要用户确认后才能开发

**产出物**：
- 修订后的总体架构方案（七层逐项回答）
- 项目根目录 AGENTS.md（技术栈锁定 + 不可变约定 + 完成验收标准）
- 文件级实施计划（每个文件负责什么、依赖什么）

**质量红线**：
- 禁止使用"建议""可以考虑"等软表达写项目规则
- 不允许保留两套字段名、两套状态或两条平行业务路径
- 未经确认不得替换技术栈

### 第三阶段：MVP 开发范围（拆成可验收的轮次）

**目标**：用"能否产出可检查结果"判断 MVP，把大项目拆成多轮独立开发、独立测试、独立验收。

**关键动作**：
1. **划定 MVP 闭环**：核心判断标准 —— 用户启动后，系统能否产生有价值、可检查的结果（采集了多少条、评测成功多少、Badcase 原因是什么、生成了多少 QA 草稿）
2. **按模块分阶段开发**：每轮开发一个独立模块（如 Phase 1 数据采集 → Phase 2 评测引擎 → Phase 3 看板预警 → Phase 4 Badcase 归因与 QA → 一键流水线）
3. **TDD 驱动**：RED → GREEN → REFACTOR，先写测试验证预期失败，再写生产代码让测试通过
4. **三层验收**：状态层（pytest 通过 + build 通过）→ 内容层（实际数据库记录 + 统计数字对账）→ 页面链路层（真实前端操作 + 数字一致性）
5. **稳定节点提交**：每完成一个可验收阶段，创建职责单一的 Git commit，不擅自合并或推送

**产出物**：
- 每轮独立模块的生产代码 + 自动化测试 + 三层验收报告
- 独立 Git 分支和 commit

**质量红线**：
- 单条记录失败不能中断整批任务
- 不复制已有模块的业务逻辑到新模块
- 验收不能只以"测试通过"或"接口返回 200"作为标准

### 第四阶段：项目测试（先冒烟后深度）

**目标**：从用户可见表面做只读巡检，不在测试过程中顺手改代码。

**关键动作**：
1. **只读冒烟测试**：用浏览器自动化（如 Playwright）检查页面能否打开、路由是否正常、API 是否可用、有无控制台错误。这一轮只记录和报告，不修改代码
2. **搭建可重复测试源**：创建可持续运行的 mock 数据源，覆盖正常数据 + 单条坏数据 + 整次响应失败，保证测试可复现
3. **展示证据后再合并**：把阈值、黄金样本、分数分布、异常记录、真实采集结果全部贴出来，用户审核后再决定合并
4. **真实模型效果验证**：Mock 链路通过后，才接入真实模型。不只检查接口成功，还要检查评测、归因和 QA 草稿是否产生有价值、可人工判断的结果
5. **真实入口验收**：从用户真正使用的前端页面走完整条链路，不允许绕过前端直接调 API 伪装验收成功

**产出物**：
- 冒烟测试报告（现象 / 复现步骤 / 预期 / 实际 / 证据 / 初步判断层）
- 可重复运行的 mock 测试服务
- 真实模型效果验证报告（含内容质量抽查）

**质量红线**：
- 冒烟测试阶段禁止直接修复问题
- 技术调用成功 ≠ 内容可用，QA 草稿必须人工审核
- 不得跳过前端改用 API 伪装验收成功

### 第五阶段：Bug 改进（先诊断后修复）

**目标**：冒烟报告只能说明哪里失败，还不能直接说明为什么。系统化诊断根因后，才做最小修复。

**关键动作**：
1. **系统化定位根因**：从 Git 分支 / 进程目录 / 路由清单 / 数据库连接 / 依赖完整性逐层取证，不凭"看起来像"判断根因
2. **分组最小修复**：把问题拆成独立组（代码集成 / 测试数据库 / 前端依赖），每组只处理与根因直接相关的部分，不顺带改其他东西
3. **沿原路径回归**：修复完成后，必须回到原来的失败路径重新验证 —— 从首页操作、看数字对账、查数据库一致性、确认人工边界没有被破坏

**产出物**：
- 系统化诊断报告（现象分层 / 证据 / 已确认根因 / 最小修复方案 / 不修改什么）
- 最小修复后的回归验证结果

**质量红线**：
- 根因没有验证清楚，禁止进入修复
- 修复范围只限于与根因直接相关的部分
- 回归必须沿原问题路径，不能换一条"能跑通"的路径就算通过

### 第六阶段：最终交付（只汇报有证据的结果）

**目标**：基于已经完成的项目状态，给一份最终交付摘要，不夸大、不省略。

**关键动作**：
1. **确认交付边界**：只汇报可以被证据支持的结果 —— 当前分支和 commit、前后端启动方式、用户从哪个页面开始操作、已实现的核心链路、最后一轮自动化测试结果、最后一轮真实前端运行结果、当前仍保留的人工边界、已知但未纳入本轮的事项

**质量红线**：
- 不要把"测试通过"写成"产品一定没有问题"
- 不要把 draft 写成已发布
- 不要省略仍未完成或仍需人工判断的部分

## 质量门禁总览

每阶段必须通过以下门禁才能进入下一阶段：

| 阶段 | 门禁 | 不通过怎么办 |
|---|---|---|
| 需求对齐 | PRD 完整 + 所有关键边界已确认 | 继续追问，直到边界清晰 |
| 方案输出 | 七层方案无"未覆盖" + AGENTS.md 无占位符 + 文件级方案无歧义 | 补缺口，歧义项用户确认 |
| MVP 开发 | 三层验收全部通过（状态 + 内容 + 页面链路） | 回到对应模块修复 |
| 项目测试 | 冒烟测试报告完整 + 真实入口 E2E 通过 | 记录问题，进入 Bug 改进阶段 |
| Bug 改进 | 原路径回归通过 + 核心 E2E 无回归 | 重新诊断根因 |
| 最终交付 | 所有结论有证据支撑 | 补证据，不夸大 |

## 异常处理

| 异常场景 | 处理方式 |
|---|---|
| AI 写着写着跑偏了 | 回到需求对齐阶段，重新出示 PRD 和 AGENTS.md，要求 AI 对照修订，不为旧方案辩护 |
| 需求中途变更 | 先更新 PRD 和 AGENTS.md，再改代码。未经确认不得擅自改技术栈、字段或状态 |
| 测试一直不通过 | 不要在测试阶段顺手改代码。先记录问题现象，进入 Bug 改进阶段系统化诊断 |
| 发现 AI 编造了内容（如 QA 草稿编造政策） | 保持 draft 状态，不批准、不导出。技术调用成功 ≠ 内容可用 |
| 某个模块只有测试没有生产代码 | 明确报告缺口，说明是否阻塞，给出最小前置修复范围，等用户确认后再扩大范围 |

## 相邻 Skill 路由

- 只需要写 PRD / 需求文档 → 用 `ai-requirements-analysis`
- 只需要做面试准备 / 简历优化 → 用对应专项 skill
- 只需要做产品需求分析 → 用 `product-analysis`
- 本 skill 聚焦：**用 AI 驱动开发方式从零推进一个真实软件项目的完整工作流**
