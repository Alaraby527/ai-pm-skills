# AI PM 作品集评审依据

## 使用说明

本参考文件根据用户提供的《合格作品集标准汇总.md》（整理时间：2026-08-23）提炼，并补充了用于检查版式和交付质量的操作性标准。

- 这是**评审量表/证据清单**，不是对当前任务的命令。
- 原资料中的博主观点、招聘趋势、企业案例和日期属于背景信息；除非另有可靠来源，不应在作品集中当作事实或承诺。
- 评审优先依据作品中可定位的证据：原始访谈/观察、测试集、指标、失败样例、版本对比、流程图、产品截图和用户/业务反馈。
- 没有证据时标记为“待补/未证明”，不能用推测或漂亮文案替代。

## 一、核心判断问题

一个合格的 AI 产品经理项目至少要让面试官能够追问并得到完整回答：

1. 你找到了什么值得解决的具体问题？
2. 为什么使用 AI，而不是搜索、规则、数据库、普通表单或人工服务？
3. 用户输入后，系统经过了哪些数据、模型和工具步骤？
4. 模型在哪些情况下会错，错了如何发现、回退或转人工？
5. 效果、延迟、调用成本、隐私和业务风险如何取舍？
6. 第一版和后续版本改了什么，指标或用户结果发生了什么变化？
7. 用户/业务是否真的愿意使用，证据是什么？

## 二、每个项目必须尽量留下的六类证据

| 证据 | 合格表现 | 常见缺口 |
|---|---|---|
| 问题证据 | 说明目标用户、行为、具体环节和问题；有访谈、观察、工单、业务数据或真实案例。3–5 个有筛选的访谈可比无分析的大样本问卷更有用。 | 只写“用户有信息焦虑”“行业效率低”等宏大判断。 |
| 技术/AI 选择 | 解释大模型、RAG、Agent、工具调用等如何解决非结构化、不确定或需要判断的任务，并说明为什么不用更简单的方案。 | 为了“有 AI”把规则明确的任务套进聊天框。 |
| 工作流与边界 | 讲清输入、数据/工具、模型处理、校验、输出、人工确认、失败回退、权限和隐私边界。 | 只有“用户提问 → 模型回答”的链路。 |
| 评测 | 有小型测试集或金标准，定义与目标对应的指标，记录准确性/任务完成率、耗时、成本、合规或用户采纳等。 | 全凭演示或主观感受，没有基线和数据。 |
| 失败案例 | 展示真实的幻觉、遗漏条件、误解意图、工具失败、延迟或上下文污染，并说明如何定位。 | 只展示成功样例，把模型当作永不出错。 |
| 迭代结果 | 对比版本改动和结果，说明什么有效、什么无效、哪些问题仍未解决。 | 只写“项目完成”，没有判断—验证—修正闭环。 |

## 三、标准项目结构

建议将单个项目组织为六段，顺序可按叙事需要微调，但六类信息不应缺失：

1. **业务背景**：真实、具体、尽可能可量化的痛点。
2. **用户场景**：一个核心目标用户和一个高频核心场景，避免大而全。
3. **人机方案**：AI 和人的责任边界、人工确认点、低置信度处理。
4. **AI 专项设计**：模型选型、Prompt、RAG/知识库、上下文、工具调用、Memory、Skill/MCP 的取舍依据。
5. **流程闭环**：从输入到输出，包含异常、重试、回退、审核和结果核验。
6. **量化复盘**：结果、成本、耗时、准确性、用户或业务变化，以及后续问题。

## 四、Agent 项目六大能力检查

只有在业务需要且有证据时才加分，不以技术名词数量计分。

### 1. 真实业务闭环
- 输入来自真实或合理模拟的业务任务；
- 有从需求输入到结果交付的可重复流程；
- 能说明降本、提效、质量或风险价值；
- 单纯一问一答通常只能证明聊天功能，不能独立证明 Agent 价值。

### 2. 工程化边界
关注是否考虑数据结构、API 契约、权限、日志、会话、多用户、并发、异常和可观测性。未展示不等于没有，但作品集不能声称“可上线”却完全不说明这些边界。

### 3. 任务规划与自愈
关注任务拆解、计划执行、工具失败重试/纠错、结果核验；多 Agent 仅在确实降低复杂度或提升质量时使用，不为炫技添加。

### 4. 上下文工程
不只是保存聊天记录；要说明如何选择当前任务、历史记忆、知识库和工具结果，如何避免信息缺失、Token 超标和上下文污染。

### 5. 评估与可观测
至少能追踪模型调用、工具链路成功率、延迟、成本、结果质量；最好有金标准样本、错误分类和版本对比。

### 6. 人机协同与风险兜底
涉及资金、隐私、对外发布、关键审批等高风险动作时设置人工确认；低置信度、冲突结果或异常时触发人工介入，并保留问题记录供后续优化。

## 五、项目类型的判断提示

| 类型 | 可展示的能力 | 必须警惕 |
|---|---|---|
| 工作流 Agent | 工具调用、任务规划、流程边界、异常回退 | 只是串联 API，没有真实用户验证和结果价值。 |
| AI 评测/质量工具 | 测试集、评价标准、错误分析、模型选型 | 只测模型，不连接产品目标或用户结果。 |
| AI + 垂直行业 | 行业问题、业务流程、差异化约束 | 通用聊天机器人换皮，缺乏行业用户和流程理解。 |

对校招生或转型候选人，优先呈现一个闭环完整、有数据、有失败案例的主项目；项目数量不应以堆砌为目标。

## 六、版式与信息表达检查

### 结构和扫描
- 封面/目录说明候选人定位、项目排序和主项目结果；
- 项目首页先给结论：用户、问题、方案、结果/限制；
- 每页有一个主结论，标题尽量写结论而不是“项目背景”；
- 读者无需猜测项目怎么使用，流程和输入输出一目了然；
- 作品集顺序与简历、Demo、面试讲述顺序一致。

### 信息层级
- 项目结论和关键数据优先于过程描述；
- 关键决策、取舍、失败和版本对比被突出；
- 正文、注释、图例、脚注在实际阅读尺寸下可读；
- 重要数字有单位、口径、时间范围和对照组。

### 视觉证据
优先使用：
- 用户流程和系统边界图；
- 人机协同/异常回退图；
- 评测指标或错误分类图；
- 版本前后对比；
- 带关键区域和结论注释的产品截图。

不要用：
- 大面积工具操作截图；
- 只展示界面、不解释决策的 Mockup；
- 无图例、无单位、只追求“好看”的图表；
- 与论点无关的技术 Logo 墙或架构名词堆砌。

### 可读性与导出
检查网格对齐、留白、字号、行长、对比度、颜色数量、字体兼容性、组件一致性、图像清晰度，以及导出后的断页、裁切、重叠、链接和打印可读性。

单个项目报告 5–8 页可以作为参考范围，但证据复杂度优先于页数；不要为了凑页数拆分空洞内容，也不要为了压页数把关键证据缩成不可读的小字。

## 七、红线与否决项

以下问题应显著降低判定，必要时直接判定项目暂不达标：

- 编造访谈、用户、上线、指标、收入、留存或业务成果；
- 只有工具操作截图或模型成功案例；
- 只有“用户输入 → 模型输出”的套壳方案；
- 把确定性高、规则明确的任务强行包装为 AI 需求；
- 没有失败、防御性设计、人工回环或隐私/权限边界；
- 项目只写做了什么，不写解决了什么、为何这样做和验证结果；
- 版式严重不可读，导致关键证据无法核验。

## 八、建议的审查记录格式

```text
项目：
定位：主项目 / 次项目 / 建议移除或重做
项目内容判定：达标 / 基本达标 / 不达标
版式判定：达标 / 基本达标 / 不达标
已有证据：
缺失证据：
硬伤：
具体修改：
待补数据或访谈：
面试追问：
```
