# AI 需求分析 Skill

## 简介

**干什么的**：把模糊的 AI 产品想法转化为清晰、可执行需求的方法论工具包。从需求澄清到 PRD 撰写，覆盖 AI 需求特有的可行性评估、参与模式设计和验收指标。

**核心方法论**：AI 需求四问澄清法 + 四维可行性评估（技术/数据/成本/合规）+ 三种 AI 参与模式（辅助/半自动/全自动）+ 3D 验收指标（Dimension/Degree/Duration）+ AI 产品设计五要点 + MVP 方案规划。

**你能得到什么**：澄清后的需求定义、可行性评估报告、AI 产品方案设计、完整 PRD 文档、三维验收指标、MVP 版本规划、灰度发布与迭代方案、风险与应对清单。


## 触发场景

当用户需要将模糊的 AI 产品想法转化为清晰、可执行的需求时触发。典型场景包括：
- 把一个模糊想法理清楚："我想做一个 AI XX，帮我理一下"
- 写 AI 产品 PRD / 需求文档
- 评估一个 AI 需求是否可行
- 设计 AI 功能的验收标准
- 规划 MVP 最小可行版本

## 输入要求

**必需信息**：
- 需求描述（哪怕是模糊的想法）
- 业务背景（给谁做、解决什么问题）

**可选补充信息**：
- 目标用户画像
- 现有产品/技术条件
- 时间/资源约束
- 相关竞品参考

**信息不全时的追问话术**：
- 缺用户场景："这个功能主要给什么人用？他们在什么场景下会用到？能举一个具体的使用例子吗？"
- 缺痛点："用户现在是怎么解决这个问题的？现有方案哪里不好？"
- 缺验收预期："这个功能做到什么程度你觉得算成功？有没有可量化的标准？"
- 缺约束条件："有没有技术、资源或合规方面的限制？比如数据不能出域、必须用某类模型等。"

## 工作流（4 步）

### Step 1：需求澄清——AI 需求四问法

用四个问题把模糊需求变清晰：

**一问：什么用户在什么场景下使用？**
- 目标用户画像（角色、行业、使用频率）
- 典型使用场景（什么时间、什么设备、什么状态）
- 触发条件（用户遇到什么问题时会想到用这个功能）

**二问：解决什么问题？**
- 核心痛点是什么
- 用户当前怎么解决的（手动/其他工具/不做）
- 现有方案的痛点和成本
- 替代方案有哪些

**三问：期望达到什么效果？**
- 验收标准（做到什么程度算成功）
- 核心指标预期
- 用户体验预期

**四问：有什么约束条件？**
- 技术约束（模型能力、技术栈、数据可得性）
- 资源约束（人力、时间、预算）
- 合规约束（数据隐私、内容安全、行业监管）
- AI 做不到时的兜底方案

> 详见 `references/prompts.md` 中的需求澄清提示词

**检查点**：四问有任一问无法回答时，先输出"需求假设版本"让用户确认或修正（见异常兜底），再进入可行性评估。

### Step 2：可行性四维评估

#### 维度一：技术可行性
- 模型能力是否支撑（当前大模型能做到吗？准确率大概多少？）
- 需要什么技术栈（纯 Prompt / RAG / 微调 / 自研模型）
- 有没有已知的技术难点

#### 维度二：数据可行性
- 需要什么数据（训练数据 / 知识库数据 / 用户行为数据）
- 数据从哪里来（自有数据 / 公开数据 / 采购数据 / 用户授权数据）
- 数据量是否足够、质量如何
- 数据标注和更新成本

#### 维度三：成本可行性
- 开发成本（人力、时间）
- 运行成本（Token 费用、算力费用）
- 维护成本（持续优化、数据更新）
- 投入产出比估算

#### 维度四：合规可行性
- 数据隐私风险（用户数据是否可用于训练）
- 内容安全（生成内容会不会有风险）
- 行业监管（特定行业有无特殊要求）
- 伦理问题（偏见、歧视、透明度）

**输出**：可行性评估矩阵（高/中/低）+ 核心风险点。任一维度为"低"时，必须给出替代方案或明确建议"不做"。

### Step 3：AI 参与模式与方案设计

#### 3.1 选择 AI 参与模式

| 模式 | 定义 | 适用场景 | 风险等级 |
|------|------|---------|---------|
| **辅助模式（Copilot）** | AI 提供建议/草稿，人做最终决策 | 医疗、金融、审批、内容创作 | 低 |
| **半自动模式（Agent）** | AI 自动处理，人工审核关键节点 | 客服回复、内容生成、数据分析 | 中 |
| **全自动模式** | AI 端到端完成，无需人工介入 | 闲聊、简单问答、任务自动化 | 高 |

#### 3.2 设计 AI 核心模块
1. **上下文设计**：给模型什么背景信息
2. **Prompt 设计**：如何引导模型输出期望结果（系统 Prompt + 任务 Prompt + 约束规则）
3. **工具调用设计**：是否需要调用外部工具
4. **知识库设计**（如适用）：知识来源、分块策略、标签体系
5. **模型选型**：用什么模型，为什么
6. **异常兜底方案**：模型答不出/答错了/置信度低时怎么办

#### 3.3 AI 产品设计五要点（必须在方案中体现）
1. **管理预期**：明确告知用户 AI 能做什么、不能做什么
2. **设计反馈闭环**：用户能纠错（"这个不对"→ 重新生成）
3. **置信度展示**：在关键场景展示 AI 的置信度，让用户判断是否信任
4. **渐进式交互**：从简单交互开始，逐步引导用户深入
5. **兜底机制**：AI 无法处理时平滑转人工或给出降级方案，不留用户"卡住"

#### 3.4 设计 MVP 最小可行版本
- 最小功能集合（必须有 vs 可以没有）
- 最快验证方式（能不能用现有工具/低代码先搭 Demo）
- 验证什么假设
- 成功标准是什么

### Step 4：输出需求文档

按 `references/template-ai-prd.md` 模板输出完整的 AI 产品需求文档，必须包含五大模块：

1. **背景与目标**：业务背景、核心目标、北极星指标、需求范围
2. **场景与流程**：用户场景、交互流程、**异常流程处理（AI 无法回答时的兜底策略）**
3. **AI 优化方案**：AI 参与模式、技术选型、Prompt 设计、知识库设计、AI 与人的分工边界
4. **评估指标**：3D 验收指标（见下方）+ 效果/业务/体验指标
5. **上线与迭代**：灰度发布策略（小流量→逐步放量）、监控看板、Bad Case 收集→分析→优化→回归测试的迭代机制

## 3D 验收指标设计方法

每个核心指标必须包含三个要素：

| 要素 | 含义 | 示例 |
|------|------|------|
| **Dimension（维度）** | 衡量什么 | 准确率、召回率、满意度、人工干预率、转化率 |
| **Degree（程度）** | 目标值 | 准确率 ≥ 92%、满意度 ≥ 85%、人工干预率 ≤ 10% |
| **Duration（周期）** | 达标时间 | 上线 3 个月内、灰度 2 周后 |

指标分三类：
- **效果指标**：准确率、幻觉率、召回率、忠实度
- **业务指标**：转化率、GMV 增量、客服成本降低、退货率
- **体验指标**：采纳率、响应时长、任务完成率、用户满意度

详见 `references/template-acceptance-metrics.md`。

## 质量红线

1. **四问法必须完整回答**，不得跳过"约束条件"一问——AI 需求的风险 80% 来自未识别的约束。
2. **可行性评估必须覆盖四个维度**（技术/数据/成本/合规），缺"数据可行性"不合格。AI 产品的数据可得性往往是最大风险。
3. **验收指标必须包含 3D 三要素**（Dimension/Degree/Duration），只写"提升用户体验"这类无目标值、无时间节点的指标不合格。
4. **PRD 必须包含异常流程和兜底方案**——AI 输出不确定，"AI 答错了怎么办"是 AI PRD 与传统 PRD 的核心区别。
5. **不编造模型能力数据**：模型准确率、响应速度等数据须来自公开 benchmark 或实际测试，不凭印象写。
6. **AI 参与模式的选择必须给出理由**，不能默认选"全自动"。

## 异常兜底

| 异常情况 | 处理方式 |
|---------|---------|
| 用户需求太模糊，四问后仍不清晰 | 给出一个"需求假设版本"让用户确认或修正，而不是反复追问 |
| 可行性评估为"低" | 明确标注风险，给出替代方案（如降级为辅助模式、缩小 MVP 范围），不硬推方案 |
| 模型能力边界不确定 | 建议先做 PoC（概念验证）测试模型能力，再决定是否进入正式 PRD |
| 用户没有数据但方案需要 RAG | 明确告知数据缺口，建议先用公开数据/合成数据验证，或调整方案为纯 Prompt |
| 合规风险无法判断 | 建议法务/安全团队评审，PRD 中标注"待合规确认"，不擅自下结论 |
