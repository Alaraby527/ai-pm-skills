# 写提示词（Prompt Writing）

按本文件的工作流产出**可直接复制运行的提示词**，不要产出只讲原理的文章。

## 底层认知（先建立，再动笔）

- 提示词是写给模型执行的**工单**，不是咒语、不是给人看的分析报告：只写“怎么做”，不写“为什么/理论名词”。模型不需要知道某个策略叫什么，只需要知道先说什么、按什么步骤、什么风格、边界在哪。
- 模型没有跨会话记忆，System Prompt 全程固定；它需要的背景、知识、示例都要在本次提示词或检索注入里给全，做到**自包含**。
- 只使用用户提供的业务事实；行业数据、案例、价格、政策一律不编造，缺了就用 `〔待补充〕` 占位并提示用户补齐。
- 抽象与具体的平衡是核心难题：太抽象模型不执行，太具体模型只会复读。给“框架 + 规则 + 少量示例”，不写逐字稿。

## 标准工作流（6 步，按序执行）

### 第 1 步：澄清任务，缺关键信息先问再写
动手前确认以下 5 项；缺关键项就一次性向用户问清，不要边写边猜。用户已给全则跳过；不影响成稿的次要模糊点，自选合理默认并在交付时标注。
1. **任务类型**：生成 / 抽取 / 分类判断 / 多轮对话 / 工具调用 / Agent 系统提示词（选型见 [task-playbooks.md](references/task-playbooks.md)）。
2. **输入样例**：要至少一段真实输入，看清输入长什么样、有哪些噪声。
3. **输出要求**：结构、字段、长度、语言、格式（纯文本 / Markdown / 表格 / JSON）。
4. **约束与红线**：不能说或不能做什么、合规要求、必须遵守的业务规则。
5. **好坏标准**：怎样算对，有没有已经出错的 bad case。

**缺哪项问哪项的追问话术（一次问全，不逐条挤牙膏）**：
- 缺任务类型：“这个提示词最终要让模型完成的是哪类事——生成内容、抽取信息、分类判断、多轮对话、调用工具，还是做一个 Agent？”
- 缺输入样例：“发我 1-2 段模型实际会收到的真实输入（可脱敏），我照着它的样子和噪声来设计。”
- 缺输出要求：“你希望结果长什么样？给个理想输出的样子，或说明字段 / 格式 / 长度 / 语言。”
- 缺约束红线：“有什么是绝不能说 / 绝不能做的，或必须遵守的规则吗？”
- 缺好坏标准：“现在有没有它答错 / 答偏的例子？发我一个 bad case，我据此对症设计。”

**可选信息及其缺省处理**：目标读者 / 使用平台 / 所用模型 / 语气偏好 / 调用方式（单轮或系统提示词）。用户没给时不阻塞成稿，按“通用读者、纯文本、模型无关、中性专业语气、单轮”取默认，并在设计说明里标注这些默认假设。

### 第 2 步：选骨架
- 简单单轮任务：套用 [assets/prompt-skeleton.md](assets/prompt-skeleton.md) 的通用五要素骨架。
- 命中具体任务类型：套用 `assets/task-templates/` 下对应模板。
- 复杂多轮对话或 Agent：先读 [task-playbooks.md](references/task-playbooks.md) 的“拆分原则”，判断用一个提示词还是“全局 + 子提示词”。

### 第 3 步：按要素写第一版
默认按**五要素**组织：角色 / 任务 / 流程 / 上下文与示例 / 输出格式；复杂对话型任务用**目标-策略-执行-约束四层架构**。逐要素写法、正反例见 [prompt-anatomy.md](references/prompt-anatomy.md)。

### 第 4 步：按任务配技巧
按需选用 Few-shot、思维链、正向表达、结构化输出、约束、自我校验等技巧，**不无脑全加**（简单任务加思维链反而画蛇添足）。技巧细节与“什么任务用什么技巧”见 [techniques.md](references/techniques.md)。

### 第 5 步：对照清单自检
用 [checklist.md](references/checklist.md) 逐项过，重点查：约束是否正反成对、每条路径是否闭环、形容词是否已量化、有没有兜底、红线是否在首尾且声明最高优先级。

### 第 6 步：配测试与迭代方案
- 附 3–10 条测试用例，覆盖常见 / 边界 / 异常（建议比例约 6 : 2.5 : 1.5）。
- 说明迭代纪律：每次只改一个变量、A/B 对比、保留版本号与变更记录。
- 诊断、评测集、Bad Case 归因方法见 [debug-and-eval.md](references/debug-and-eval.md)。

## 五要素速查（写第一版的最小骨架）

1. **角色**：一句话定义身份 + 能力边界（能做什么 / 不能做什么）。
2. **任务**：一句话说清要完成什么、达成什么目标（目标尽量唯一）。
3. **流程**：编号步骤，每步单一动作；只有需要推理的复杂任务才写分步思考。
4. **上下文与示例**：给必要背景与知识；输出格式固定或模型容易跑偏时，给 3–5 个 Few-shot（含正常、边界、异常各类型）。
5. **输出格式**：明确结构、字段、长度、语言；需要程序解析时直接给 JSON Schema 并给出示例。

复杂多轮 / Agent 任务改用“目标层—策略层—执行层—约束层”四层架构，详见 [prompt-anatomy.md](references/prompt-anatomy.md)。

## 写作铁律（高频出错点，逐条遵守）

- **指令可执行、去形容词**：写“每轮 2–3 句、不超过 50 字”，不写“简短 / 适当 / 热情”这类模型无法对齐的形容词；不能量化就给一个示例。
- **正反成对**：关键规则把“能做什么 + 不能做什么 + 越界时怎么处理”一起写，不能只写一半。
- **路径闭环**：每个“如果…就…”都要有明确出口，不留走到一半没指令的死胡同；每个可重复策略写清“触发 + 执行 + 退出（最多几次）”；为指令未覆盖的场景设计统一兜底。
- **冲突给优先级**：两条规则可能打架时，明确“冲突时谁优先”。
- **约束放首尾**：最重要的红线放开头或结尾（模型对首尾注意力更强），并声明其最高优先级、任何策略不得突破。
- **抽象-具体平衡**：给框架与表达规则，不写死整句话术，否则模型机械复读；风格靠“规则 + 正反对比示例”传达。
- **信息按需释放**：不要一轮堆砌全部信息，每轮只推进一个新信息点，先给钩子、追问后再展开。
- **自包含、控长度**：不依赖“你懂的”这类外部上下文；核心指令尽量精炼（经验上 2000 token 内更稳），但**完整性优先于精简**——红线、目标、风险应对绝不能为变短而删。

## 特殊情况处理（异常兜底）

| 情况 | 处理方式 |
|------|---------|
| 用户多个目标相互冲突 | 不擅自合并，明确指出冲突，请其指定唯一主目标，其余降为约束 |
| 用户只要一句提示词 | 只给可直接用的正文，省略设计说明与测试用例，但一句话提示“可再补测试迭代” |
| 用户给的是效果不好的旧提示词 | 不直接重写，先走 [debug-and-eval.md](references/debug-and-eval.md) 定位病因，再对症改，并保留旧版做 A/B |
| 没有真实输入样例 | 先给可套用版本，把输入相关处写成 `{{占位符}}`，并提示补样例后再补 Few-shot，不凭空编造样例 |
| 缺少业务事实 / 数据 | 不编造，在提示词相应位置写 `〔待补充〕` 并在交付说明里列出需要用户补什么 |
| 用户语言 / 行业特殊 | 提示词正文跟随用户要求的语言；行业术语只在用户提供时使用，不自行引入 |
| 本 Skill 是纯方法库 | 不替用户调用外部工具或检索；需要外部事实时请用户提供材料，仅基于所给材料写 |

## 交付格式

默认一次给齐三样，用户只要其中某一样时从其要求：
1. **提示词正文**：放在代码块里，可整段复制；需要用户填的地方用 `{{占位符}}` 标出。
2. **设计说明**：简短说明用了哪些要素 / 技巧、关键设计为什么这样处理。
3. **测试用例与迭代建议**：覆盖常见 / 边界 / 异常的样例输入与预期输出要点，以及后续怎么做 A/B 与版本管理。
