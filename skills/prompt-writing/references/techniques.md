技巧是按需取用的工具，不是越多越好。先判断任务真正缺什么，再加对应技巧。

## 一、六大基础技巧

### 1. Few-shot（少样本示例）
- **解决什么**：输出格式不稳、风格不一致、模型“没理解要什么”。
- **怎么写**：
  - 给 3–5 组成对的「输入 → 期望输出」，格式与真实运行完全一致。
  - 样本要覆盖三类：**正常情况、边界情况、异常 / 容易出错的情况**，不能只给最顺手的例子，否则模型在边界上崩。
  - 样本之间保持同一输出结构；想让模型学到的规则，要在多个样本里一致体现。
  - 样本去业务化无关细节、去掉相互矛盾的个例；不要用样本偷偷塞互相冲突的规则。
- **抽象示例骨架**：
  ```
  示例1（正常）
  输入：{{一条典型输入}}
  输出：{{对应标准输出}}
  示例2（边界：两种类别都像）
  输入：{{}}
  输出：{{按裁决规则输出}}
  示例3（异常：信息缺失）
  输入：{{}}
  输出：{{走兜底，而不是硬答}}
  ```
- **何时不用**：任务极简单、纯开放创作且不要求固定格式时，加示例反而限制发挥。

### 2. 思维链（CoT）/“先想再说”
- **解决什么**：需要多步推理、分类裁决、复杂判断时直接给答案容易错。
- **两种用法**：
  - *显式分步*：`请按步骤分析：1.… 2.… 3.…，最后给出结论。`适合可展示推理过程的任务。
  - *内部判断*（对话 / Agent 更常用）：要求模型每次回复前先在内部完成判断，再输出给用户的话。
    ```
    每次回复前，先内部判断（不要把判断过程发给用户）：
    1. 当前处于哪个阶段 / 用户意向程度；
    2. 用户未明说的顾虑是什么；
    3. 现在该推进还是先回应顾虑；
    4. 该调用哪个技能模块。
    判断完再组织回复。
    ```
- **何时不用**：一步就能答的简单任务加 CoT 会拖慢、啰嗦，属画蛇添足。要求最终只输出 JSON / 标签时，让推理进单独字段（如 reason）或内部完成，别污染结构化输出。

### 3. 正向表达（说“要做什么”，而不只是“别做什么”）
- 模型对否定指令遵循较差，单纯禁止常导致“不知道该干嘛”。
- 每条禁令尽量补“那应该怎么做”，必要时补一句原因（原因能提升遵循度）。
- 反例：`不要说太多。`
- 正例：`每轮只回答用户当前问的这一点（避免信息过载）；其余信息等用户追问再展开。`
- 必须禁止的高危项仍要明确写“禁止 X”，并配“改为 Y”，形成正反成对。

### 4. 结构化输出
- **解决什么**：结果要被程序解析、要填表格、要稳定可比。
- **怎么写**：
  - 指定载体（JSON / Markdown 表格 / 固定分节），逐字段给名称、取值范围、是否必填、含义。
  - 给一个完整输出样例；声明“只输出该结构，不要额外解释 / 前后缀”。
  - 取值封闭时用枚举：`字段 label 只能取 A | B | C | 无法判断`。
  - 需要工具调用时用 JSON Schema 定义参数，字段与工具接口一一对应（见 [task-playbooks.md](task-playbooks.md)）。
- **要点**：结构是“硬约束”，字段一旦定了，Few-shot 里的输出字段必须和它完全一致。

### 5. 约束条件
- 包括：长度 / 数量上限、语言与语气、不能使用的内容、必须引用给定资料、动作次数上限（如“最多追问 3 轮”）等。
- 写法要求见 [prompt-anatomy.md](prompt-anatomy.md) 第五节：可判定、正反成对、冲突给优先级、红线放首尾。
- 约束要少而硬：挑真正影响成败的写，泛泛的“要专业、要高质量”没有可执行性，删掉。

### 6. 自我校验（Self-check）
- 在输出前让模型按清单自查一遍，显著降低格式错误和自相矛盾。
- 写法：
  ```
  输出前自检，任一不满足就修正后再输出：
  - 是否每个必填字段都有值、取值都在允许范围内；
  - 结论是否都能在【参考资料】中找到依据，没有就改为“暂无信息”；
  - 是否与上文已确认的信息矛盾；
  - 是否满足全部约束（长度 / 条数 / 禁止项）。
  ```
- 适合：事实性强、格式刚性、错误代价高的任务。纯创意任务可省。

## 二、表达风格控制

当任务对“读起来像什么”有要求（如口语化、正式、简洁）时，**不要只丢一个形容词**，要用“规则 + 正反对比示例”双重锚定。

- 反例（太抽象）：`语气要自然、像真人。`
- 正例（规则 + 对比）：
  ```
  表达风格：
  - 用口语短句，一句话不超过约 25 字；可自然使用语气词，但不要每句都加；
  - 用“咱们/您”，不用书面化长句和机械重复；
  - 对比：
    机械：感谢您的咨询，我方将竭诚为您服务。
    自然：没问题，这个我帮您看一下哈。
  - 禁止：书面腔、套话堆砌、过度礼貌、同一句话换词重复。
  ```
- **信息按需释放**：不要在一轮里把所有信息倒完。先给“钩子 / 结论”，用户追问再逐层展开，每轮只新增一个信息点。把这条显式写进提示词。

## 三、提示词与配置分离

- **提示词管“内容”**：怎么判断、怎么说、用什么策略、什么风格。
- **配置管“系统行为”**：何时结束、何时转人工、调用哪个接口、超时与重试、温度等模型参数。
- 不要把结束会话 / 转人工 / 页面跳转等系统触发条件全塞进自然语言提示词；把它们放到独立配置，提示词里只写与之对齐的处理逻辑。
- **两边必须对齐**：提示词里每个“结束 / 转出”节点，在配置里要有对应触发条件；配置里每个触发条件，提示词里要有对应处理，避免“刚要继续推进就被系统结束”这类互相矛盾。
- 模型参数经验：要求稳定、事实准确、分类抽取时调低温度（如 0.2–0.4）；开放创作可适当调高。参数属于配置，不写进自然语言正文。

## 四、任务类型 → 技巧选型

| 任务类型 | 首选技巧 | 关键提醒 |
|---|---|---|
| 信息抽取 | 结构化输出 + Few-shot（含缺失样例）+ 自我校验 | 字段封闭枚举；抽不到给 null / “未提及”，不许猜 |
| 文本生成 / 改写 | 角色 + 风格规则与正反例 + 正向表达 + 约束 | 给清目标读者和用途；用规则+示例代替“写好点” |
| 分类 / 判断 | 结构化输出 + 类别穷举定义 + 易混边界裁决 + Few-shot | 必须有“无法判断 / 其他”兜底类；两可时写裁决规则 |
| 多轮对话 | 四层架构 + 三层设计法 + 内部判断 + 触发条件闭环 | 每策略有触发/执行/退出；追问轮数设上限；留兜底 |
| 工具调用 / Function Call | JSON Schema 结构化输出 + 参数说明 + 选工具的判别规则 + Few-shot | 缺参数时先澄清再调用；工具返回为空的处理要写明 |
| Agent 系统提示词 | 四层架构 + 能力边界 + 模块化技能 + 约束层 + 拆分原则 | 见 [task-playbooks.md](task-playbooks.md)，非必要不拆分 |

## 五、使用克制原则

- 先写最简版本（角色 + 任务 + 输出格式）跑一遍，**哪里出错再用对应技巧补哪里**，不要一上来堆叠全部技巧。
- 一次只引入一种改动，便于定位是哪个技巧起了作用（迭代纪律见 [debug-and-eval.md](debug-and-eval.md)）。
- 技巧之间冲突时以“稳定达成任务目标”为准：例如要严格 JSON，就把 CoT 收进 reason 字段而非自由展开。
