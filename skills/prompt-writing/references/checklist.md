# 交付前自检清单

交付任何提示词前逐项过一遍；任一不满足，先改再交付。勾选式使用，括号内是对照依据。

## 一、要素完整性
- [ ] 有明确角色，且写清了“能做 / 不能做”的边界。
- [ ] 任务是一个可检验的交付物，主目标唯一（多个目标已分主次或拆分）。
- [ ] 需要分步的任务有编号流程，每步单一动作；简单任务没有硬塞分步。
- [ ] 必要背景 / 知识已给全，提示词自包含，不依赖“你懂的”。
- [ ] 输出格式明确：结构、字段、长度、语言；需程序解析时给了 JSON Schema 和样例。
- [ ] 复杂多轮 / Agent 任务用了四层架构（目标 / 策略 / 执行 / 约束），而不是要素平铺。

## 二、健壮性（对照七大幻觉根源）
- [ ] 关键规则正反成对：能做什么 + 不能做什么 + 越界时怎么办。
- [ ] 路径闭环：每个“如果…就…”都有出口，所有分支状态都被覆盖，没有走到一半没指令的死胡同。
- [ ] 每个可重复动作写了“触发 + 执行 + 退出（最多次数）”，不会无限循环。
- [ ] 可能打架的规则给了优先级。
- [ ] 有统一兜底：超范围 / 没听懂 / 信息缺失 / 未知分支分别怎么处理。
- [ ] 多轮任务会继承已确认信息，不重复询问。
- [ ] 若有外部配置（结束 / 转人工 / 调接口），提示词与配置逐条对齐、不矛盾。

## 三、可执行性
- [ ] 没有“简短 / 适当 / 热情 / 专业 / 充分”这类不可对齐的形容词；已量化或给示例。
- [ ] 风格要求用“规则 + 正反对比示例”表达，而不是一句“要自然 / 要口语化”。
- [ ] 没有写死整句话术导致复读；给的是框架与规则（抽象-具体平衡）。
- [ ] 分类 / 枚举类别穷举、MECE，写了易混边界裁决，并含“其他 / 无法判断”兜底类。
- [ ] 抽取 / 工具调用场景写清“抽不到 / 参数缺失 / 返回空”时的处理，且不许臆造。
- [ ] 事实性任务限定了来源，未命中要求如实说明，不用模型记忆补全。

## 四、约束与安全
- [ ] 红线放在开头或结尾，并声明最高优先级、策略不得突破。
- [ ] 区分了“硬性禁止”与“尽量偏好”，真正的红线没有被一堆软要求稀释。
- [ ] 没有编造任何用户未提供的业务数据、案例、价格、政策；缺口用 `〔待补充〕` 标注。
- [ ] 信息按需释放，没有一轮堆砌全部内容。

## 五、评测与可迭代
- [ ] 附了 3–10 条测试用例，覆盖常见 / 边界 / 异常（约 6 : 2.5 : 1.5）。
- [ ] 每条用例有可核对的预期，而不是“感觉对就行”。
- [ ] 说明了迭代方式：每次只改一个变量、A/B、固定评测集回归、留版本记录。
- [ ] 长度合理（核心指令尽量精炼），但红线、目标、风险应对没有为变短而删。

## 六、提示词坏味道（出现即改）
- 头衔堆砌但没有能力边界（“你是资深顶级专家”后面没有能做 / 不能做）。
- 通篇形容词和口号（“高质量、专业、完美”），没有可执行动作与判定标准。
- 只有一串“不要……”，却没说“那要怎么做”。
- 一个段落塞多个目标、多种格式、多重风格，模型抓不住主次。
- 示例全是最顺手的正常情况，没有边界和异常样例。
- 示例输出字段与正文要求的字段对不上。
- 写死大段逐字话术，模型在任何上下文都复读同一句。
- 分类没有兜底类、流程没有退出条件、工具调用没有失败分支。
- 要求输出 JSON，却又让它“顺便解释一下”，导致输出无法解析。
- 让模型“根据你的知识回答”本应限定来源的事实性问题。
- 优化后提示词更短更好看，但某条约束 / 风险应对悄悄消失。
