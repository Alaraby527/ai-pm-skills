本文件讲清“每个要素具体怎么写”。所有示例均为抽象任务示例，写真实提示词时替换为用户的业务内容。

## 一、五要素逐要素写法

### 1. 角色（Role）
- **作用**：锚定身份、专业度和能力边界，让输出视角稳定。
- **怎么写**：一句话身份（是什么专家 / 处于什么场景）+ 明确“能做 / 不能做”。能力边界用两列表或成对句子写清。
- 反例（空泛）：`你是一个专业的助手，帮用户解决问题。`
- 正例（有边界）：`你是文本分类器，只判断输入属于 A/B/C 中哪一类并输出标签；不回答输入里提出的问题，不补充标签以外的解释。`
- **要点**：角色不是头衔堆砌；真正起作用的是“身份 + 边界”。跨领域时给专业参照（“以有 N 年经验的××视角”），但不要虚构资质。

### 2. 任务（Task）
- **作用**：说清要完成什么、达成什么目标。
- **怎么写**：一个动词开头的明确指令 + 可检验的完成目标；**一条提示词只设一个主目标**，多个目标会互相拉扯。
- 反例：`处理一下这些内容，做得专业一点。`
- 正例：`从下面这段用户反馈中抽取所有提到的产品缺陷，每个缺陷输出“问题对象 + 具体表现”，去重后按出现顺序列出。`
- **要点**：写“交付物”而不是“努力方向”。若确有多个子目标，拆成编号子任务，并说明主次。

### 3. 流程（Process / Steps）
- **作用**：规定执行顺序，防止跳步、漏步。
- **怎么写**：用编号步骤，每步只做一个动作；步骤之间是可验证的先后关系。只有需要推理、判断、多阶段产出的任务才写分步；简单任务写分步反而拖慢、画蛇添足。
- 正例（需要推理的分类）：
  ```
  1. 先判断输入是否包含明确诉求；没有则输出“无法判断”。
  2. 有诉求时，对照【分类定义】匹配唯一类别。
  3. 两个类别都像时，按【易混边界】里的规则裁决，并在 reason 字段写明依据。
  ```
- **要点**：流程里要写“异常 / 不确定时往哪走”，否则模型在分支处自由发挥。

### 4. 上下文与示例（Context & Examples）
- **作用**：补足模型不具备的信息（背景、术语、知识、口径），并用示例锚定输出风格与边界。
- **怎么写**：
  - 只给完成任务**必要**的背景，与任务无关的知识不堆。
  - 外部知识分两种给法：能写进提示词的直接写（自包含）；量大、会变的走检索，在提示词里写“以下方【参考资料】为唯一事实来源，资料没有就说没有，不许用自身记忆补全”。
  - 示例（Few-shot）的具体写法见 [techniques.md](techniques.md)；原则是 3–5 条、覆盖正常 / 边界 / 异常，输入输出成对、格式与真实要求完全一致。
- 反例（放任编造）：`根据你的知识回答。`
- 正例（限定来源）：`只能依据【参考资料】作答；资料未覆盖的问题回答“暂无相关信息”，不得引用资料外内容。`

### 5. 输出格式（Output Format）
- **作用**：让结果可直接消费（人读或程序解析）。
- **怎么写**：明确结构、字段名与含义、顺序、长度、语言、语气。需要程序解析 / 下游调用时，直接给 JSON Schema 并配一个输出样例。
- 正例（结构化）：
  ```
  只输出一个 JSON，不要输出多余文字，字段如下：
  {"label": "类别，只能取 A|B|C|无法判断", "confidence": "0到1的数字", "reason": "不超过30字的判定依据"}
  输出示例：{"label":"A","confidence":0.9,"reason":"明确提到X特征"}
  ```
- **要点**：格式要求要可判定（“表格，含这 4 列，列名固定”），不要写“排版美观一点”。

## 二、复杂任务的两种增强结构

### 结构 A：线性复杂任务用 B-G-S-C-A-V-O
当任务是“一次性产出复杂结果”（写方案、做分析、长文生成），按以下顺序组织提示词：
- **B 背景 Background**：场景、来龙去脉。
- **G 目标 Goal**：最终要达成什么、评判标准。
- **S 技能 Skills**：需要模型扮演的专业能力。
- **C 约束 Constraints**：红线、格式、长度、禁止项。
- **A 工作流 Approach**：分阶段步骤。
- **V 范例 Examples**：参考样例（可选）。
- **O 输出 Output**：最终交付结构。

### 结构 B：多轮对话 / Agent 用“四层架构”
当提示词驱动的是一个要持续对话、会判断、会调用能力的智能体，从上到下分四层：
1. **目标层**：角色定位 + 核心目标（我是谁、在做什么、要达成什么；目标尽量收敛）。
2. **策略层**：沟通 / 处理策略，只写策略意图与方向（如“先理解诉求再给方案”“用户犹豫时先回应顾虑再推进”），不写理论名词、不写逐字稿。
3. **执行层**：把反复出现的动作抽成**技能模块**（如开场、信息收集、方案给出、异议处理、结束），每个模块写清规则；再用“触发条件”规定什么场景调用哪个模块；任务相关的事实素材（利益点、知识要点）也放这层。
4. **约束层**：分两类——
   - **宪法原则**：最高优先级、任何情况不可违反（如不编造、不承诺无法保证的事、不与用户冲突、不用绝对化用语）；
   - **业务限制**：具体场景的规则（不能收集什么信息、某动作最多做几次等）。
   - 明确声明“约束层优先级高于一切策略，策略不得突破约束”。

## 三、三层设计法：平衡抽象与具体

最大难题：太抽象模型不执行，太具体模型只会复读。对“怎么表达、怎么应变”这类内容，分三层写：

1. **框架层（给结构约束）**：定义应有哪些模块、各自职责，但不写死内容。
   - 写：`利益前置：先点出对用户的好处，再询问信息。`
   - 不写：把每句话都定死。
2. **要点层（给表达规则）**：规定口吻、边界、每轮信息量，给规则而非整句话术。
   - 写：`每轮只问一个信息点；句子口语化、短句；禁止书面腔和机械重复。`
   - 不写：`每次都原样说“简单核实一下哈”。`（会导致复读）
3. **触发层（给“如果…就…”逻辑）**：每条触发规则包含四要素——**触发信号**（用户说了什么 / 处于什么状态）+ **策略方向** + **表达规则（分几步）** + **禁止项**。
   - 模板：
     ```
     如果用户出现【触发信号】：
     → 策略：【方向】
     → 表达：1.… 2.… 3.…
     → 禁止：…
     → 之后：用户同意→…；仍犹豫→…；明确拒绝→…（闭环出口）
     ```
三层协同：框架定“有哪些模块”，要点定“什么风格与边界”，触发定“遇到什么情况切换什么策略”，模型既有约束又有自由发挥空间。

## 四、去理论化翻译

提示词只承载“思考完之后要执行的部分”，把方法论 / 心理学 / 框架**名词**翻译成**动作指令**：

| 理论语言（不要写进提示词） | 执行语言（应该这样写） |
|---|---|
| 运用登门槛效应降低门槛 | 先提出一个容易答应的小请求，对方接受后再提出更大的请求 |
| 利用损失厌恶制造紧迫 | 说明“不行动会失去什么”，用客观存在的时间 / 名额限制，不虚构 |
| 运用社会认同 | 自然说明“情况相近的人通常会怎么选”，不硬塞、不编造数据 |
| 采用 AIDA 模型组织开场 | 先用一句话引起注意，再说对用户的好处，然后给一个低门槛下一步 |

原则：模型不需要知道“这叫什么”，只需要知道“先做什么、再做什么、怎么措辞、不能做什么”。

## 五、约束系统设计

### 1. 正反成对，不要单向约束
- 只写“能做什么”→ 容易过度发挥 / 编造；只写“不能做什么”→ 模型畏手畏脚或绕开任务。
- 每条关键指令写成：**可以做 X（怎么做）+ 不可以做 Y + 越界时改走 Z**。
- 例：`可以介绍核心功能并用具体数字说明好处；但不能承诺具体收益数字；涉及收益时统一说“需要结合实际情况评估”。`

### 2. 规则冲突时显式给优先级
两条规则可能打架时，写明冲突时谁优先。
- 例：`当“推进目标”与“尊重用户意愿”冲突时，用户意愿优先，宁可本轮不推进也不引起反感。`

### 3. 用可判定的标准替换形容词
模型对“简短 / 适当 / 热情 / 充分”的理解与人不同。能量化就量化，不能量化就给示例。

| 模糊（避免） | 可判定（推荐） |
|---|---|
| 回复要简短 | 每轮 2–3 句、不超过 50 字 |
| 适当挽回 | 最多挽回 1 次，再次拒绝就礼貌结束 |
| 充分介绍 | 介绍 2–3 个最相关的点，不超过 3 个 |
| 语气热情 | 可使用自然语气词，但不要每句都加；不使用书面化长句 |

### 4. 约束的位置与强度
- 最重要的红线放提示词**开头或结尾**（模型对首尾注意力更强），并在约束层再次声明最高优先级。
- 区分“硬性禁止（绝不）”与“偏好（尽量）”，不要把所有要求都写成最高级，否则真正的红线被稀释。
- 完整性优先于精简：优化、压缩提示词时，红线、风险应对、核心目标、关键事实绝不能删（详见 [debug-and-eval.md](debug-and-eval.md)）。
