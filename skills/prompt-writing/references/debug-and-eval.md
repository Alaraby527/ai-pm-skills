提示词不是一次写对的，是“先跑起来、用 bad case 驱动改对”的。诊断永远先于改写：先定位是哪一层的问题，再动对应的部分，不要凭感觉整体重写。

## 一、三步调试法

1. **搭基线**：先用五要素写出能跑通的最简版本（角色 + 任务 + 输出格式即可起步），不追求一次完美。
2. **跑测试**：用一组覆盖常见 / 边界 / 异常的输入实际运行，收集输出与 bad case，而不是靠阅读提示词脑补效果。
3. **对症下药**：按下表定位问题层级，只改对应部分；改完用同一批测试回归，确认问题消失且没有引入新问题。

优化优先级（从便宜到昂贵，依次尝试，不要上来就换模型）：
**指令清晰度 → 补示例（Few-shot）→ 明确输出格式 → 调整结构 / 拆分 → 补外部知识（检索 / 上下文工程）→ 最后才考虑换更强模型。**

## 二、七大幻觉根源速查

模型说错、编造、行为异常，多数是提示词有结构性缺陷，逐条对照：

| 根源 | 一句话判断 | 解法 |
|---|---|---|
| 单向约束 | 只写了能做什么，或只写了不能做什么 | 正向引导 + 负向护栏成对，并写“越界时改走什么” |
| 逻辑不闭环 | 某条“如果…就…”走到一半没有下一步（死胡同） | 穷举该分支的所有结果状态，各给出口；提示词与外部配置（结束 / 转人工）逐条对齐 |
| 指令冲突 | 两条规则互相矛盾 | 显式给优先级，写明冲突时谁让谁 |
| 缺退出条件 | 某策略只有触发、没有停止（反复追问 / 挽回） | 每个策略 = 触发 + 执行 + 退出（含最多次数） |
| 指令模糊 | 用了“简短 / 适当 / 热情 / 充分”等形容词 | 能量化就量化，不能量化就给示例 |
| 信息过载 | 一个回合塞入太多信息 | 按需释放，每轮只给一个新信息点，先钩子后展开 |
| 无兜底 | 遇到没覆盖的场景模型只能自己编 | 设计统一安全出口（超范围 / 没听懂 / 未知分支分别怎么说、怎么回到主线） |

## 三、常见 Bad Case 症状 → 药方

| 症状 | 优先改这里 | 具体做法 |
|---|---|---|
| 没理解任务、答偏 | 任务描述 + 示例 | 把任务写成可检验的交付物；补正常 / 边界 / 异常 Few-shot；用正向表达替代单纯禁止 |
| 不按步骤、跳步漏步 | 流程 | 编号步骤、每步单一动作；把大流程拆成各含 3–5 步的多个提示词，用工作流串联 |
| 输出不专业、缺知识 | 上下文（不是换措辞） | 动态注入领域知识 / 检索资料，并声明“只以给定资料为事实来源” |
| 编造事实（幻觉） | 来源约束 + 兜底 | 限定事实来源、要求标注依据、未命中就说“暂无信息”；查第二节七根源 |
| 格式不稳定 / 不按格式 | 输出格式 | 给 JSON Schema / 固定分节 + 一个完整样例，声明“只输出该结构”；配格式类 Few-shot |
| 答非所问 | 角色边界 + 分类 | 收窄角色与任务；先做意图判断再处理；加“与任务无关时如何回应” |
| 输出过长啰嗦 | 约束 | 给可判定上限（句数 / 字数 / 条数）；要求“先结论后展开”；删掉无意义铺垫要求 |
| 机械复读同一句 | 抽象-具体平衡 | 删掉写死的逐字稿，改成表达规则 + 正反例（见三层设计法） |
| 自相矛盾 | 自我校验 | 输出前增加一致性自检步骤；冲突规则给优先级 |

## 四、优化诊断与“完整性优先于精简”

### 优化前先按 7 个维度诊断
结构（是否清晰分层还是一锅堆）、固化程度（是否写了太多死话术导致复读）、示例（太少没风格 / 太多只会抄）、抽象度（策略意图是否抽象到不执行）、说服 / 处理策略（是否全程一个调子硬推）、触发条件（关键场景有没有“如果…就…”）、关键约束（红线是否还在）。

### 可以精简 vs 绝不能删
- **可以精简**：重复表述、过度细化的阶段划分、多个雷同示例、冗长背景铺垫。
- **绝不能为变短而删**：限制条件 / 合规红线、风险与异常应对、行业硬性要求、业务约束（次数 / 边界）、核心利益点或关键事实、对话 / 任务核心目标。
- 最常见优化事故：把提示词压缩得很“清爽”，却顺手删掉某条约束，随后模型开始越界。**每次精简后用下面清单回查**：限制条件在不在？风险应对在不在？行业红线在不在？业务约束在不在？删掉的是否确实只是冗余？精简后是否仍完整可执行？

## 五、评测体系搭建

### 三层指标（从技术到业务）
1. **技术层**：格式合规率、JSON 可解析率、字段完整率、延迟 / 长度。
2. **过程层**：意图 / 分类准确率、步骤遵循率、事实正确率（命中率 / 幻觉率）、约束遵循率。
3. **业务层**：任务成功率、用户满意度、转化 / 解决率等真实结果指标。
先保证技术层，再看过程层，最后用业务层验收；不要用业务结果直接调提示词，中间隔着太多因素。

### 评测集怎么建
- 规模：起步 20–50 条即可跑 A/B；正式上线建议积累到百条级并持续回流真实 bad case。
- 构成比例（经验值）：**常见场景约 60%、边界场景约 25%、异常 / 对抗场景约 15%**，三类都要有，不能全是顺手的正常例子。
- 每条用例包含：输入、期望输出 / 判定标准、所属类别；判定标准尽量可客观核对。
- 固定同一批评测集做回归，不同提示词版本才有可比性。

### 怎么评
- **A/B 对比**：同一批评测集分别跑新旧版本，逐题对比，量化各指标差异。
- **LLM-as-Judge**：主观质量维度可用更强模型按给定评分量规打分，但要给量规、可抽检复核，不能只听单一评分。
- **人工抽检**：高风险场景（合规、事实）必须人工复核。

### Bad Case 四层归因（定位问题到底在哪一层）
1. **表现层**：现象是什么（先如实记录，不急着归因）。
2. **策略层**：流程 / 规则 / 触发条件设计是否有缺陷。
3. **数据 / 知识层**：是不是缺知识、检索没召回、示例覆盖不到。
4. **模型层**：是否能力上限问题。
修复成本由低到高：**补数据 / 知识 < 改策略 / 提示词 < 换模型**，按此顺序排查，能靠补知识或改提示词解决的，不要归咎于模型。

## 六、迭代纪律与版本管理

- **每次只改一个变量**：一轮只动一处（指令 / 示例 / 格式其一），否则无法归因是哪处起效。
- **保留版本记录**：版本号、日期、改了什么、为什么改、评测结果，逐条登记；出问题可回滚。
- **回归测试**：新版本必须在固定评测集上全量回归，确认目标 bad case 修好且旧能力没退化，再上线。
- **闭环回流**：线上新出现的 bad case 持续补进评测集，评测集随业务长大。
- 迭代流程固化为：**收集 bad case → 四层归因 → 只改对应一处 → 评测集回归 → 记录版本 → 上线**。
