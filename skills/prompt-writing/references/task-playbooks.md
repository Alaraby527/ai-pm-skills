每类给出“必备要素、组织方式、典型坑”。可复制的填空模板在 `assets/task-templates/` 对应文件里。先判准任务类型，类型判错，技巧全错。

## 1. 信息抽取
**任务特征**：从非结构化输入中抽出结构化字段（实体、属性、事件、观点）。

**必备要素**
- 逐字段定义：字段名、含义、取值类型 / 枚举、是否必填、多个时如何处理（去重 / 列表 / 取最近）。
- 抽不到时的统一出口：`未提及 → null（或“未提及”），禁止根据常识补全`。
- 输出为 JSON；配 1 条正常 + 1 条字段缺失 + 1 条有噪声 / 指代的 Few-shot。
- 自我校验：字段齐全、枚举合法、值都能在原文找到对应。

**典型坑**
- 没定义“抽不到怎么办”→ 模型硬猜。
- 字段含义有歧义（如“时间”是发生时间还是提及时间）→ 用一句话消歧并给例。
- 输入含多个对象时没说抽全部还是抽主要 → 明确“逐个抽取、输出数组”。

## 2. 文本生成 / 改写
**任务特征**：写 / 改写文案、摘要、邮件、报告、回复等。

**必备要素**
- 角色 + **目标读者 + 使用场景**（同一个主题，写给专家和写给新手完全不同）。
- 明确交付物：体裁、结构分节、篇幅（字数 / 条数，给区间）、语言与语气。
- 风格用“规则 + 正反对比示例”，不用“写得好一点 / 专业一点”。
- 事实约束：哪些信息必须包含、只能使用给定材料、不许新增数据。
- 改写类任务写清“保持什么不变”（如事实、结论、人称），只改指定维度。

**典型坑**
- 只给主题不给读者和篇幅 → 输出忽长忽短、详略失当。
- “适当润色”无边界 → 模型改掉原意；应写“只优化表达，不增删观点、不改变结论”。
- 一次要求兼顾太多风格 → 拆成主风格 + 最多 2 条补充要求。

## 3. 分类 / 判断
**任务特征**：打标签、判意图、做是非或等级判断、路由。

**必备要素**
- **类别穷举且 MECE**：列出全部类别，每类给可操作的判定定义（不是类别名的同义反复）。
- **易混边界裁决规则**：把“两类都像”的情况单独写清归哪类、为什么（这是分类准确率的关键）。
- 兜底类：必须有 `其他 / 无法判断`，并定义何时走兜底。
- 输出：标签（封闭枚举）+ 可选置信度 + 简短依据；配覆盖各类与易混点的 Few-shot。
- 需要稳定时调低温度。

**典型坑**
- 类别定义互相重叠又没裁决规则 → 标签飘忽。
- 没给兜底类 → 模糊输入被硬塞进某类。
- 类别数量过多（一级就十几类）→ 建两级体系：先判大类再判子类；纯提示词分类有天花板，长期应回流修正样本。

## 4. 多轮对话
**任务特征**：要连续对话、追问、根据用户状态调整策略（客服、咨询、引导、访谈）。

**必备要素（用四层架构 + 三层设计法，详见 prompt-anatomy.md）**
- 目标层：角色 + 唯一主目标。
- 策略层：分阶段策略意图，不写理论名词。
- 执行层：把开场 / 信息收集 / 给方案 / 处理异议 / 结束抽成技能模块；每轮只推进一个信息点。
- 触发层：为每种典型用户状态写“触发信号 → 策略 → 分几步表达 → 禁止 → 出口”，**所有分支必须闭环**。
- 约束层：宪法原则 + 业务限制（含追问 / 挽回次数上限）。
- 内部判断：每轮回复前先判断用户阶段与意向，再组织语言。
- 兜底：听不懂、超范围、进入未知分支时的统一安全话术与回到主线的方法。

**典型坑**
- 只写“用户拒绝时挽回”，没写挽回几次、之后怎么办 → 死循环或强推。
- 写死整句话术 → 机械复读；应给规则不给逐字稿。
- 忘记继承上下文（用户前面说过的信息反复再问）→ 写明“已确认信息直接沿用，不重复询问”。

## 5. 工具调用 / Function Call
**任务特征**：模型要选择并调用外部工具 / API，或输出结构化指令给下游执行。

**必备要素**
- 工具清单：每个工具的用途、什么情况用、什么情况**不**用（工具间易混时写选择优先级）。
- 参数用 JSON Schema 定义：字段、类型、必填、枚举、缺省规则。
- 缺参处理：必填参数缺失时先向用户澄清，不要编造参数值；澄清到齐再调用。
- 结果处理：工具成功如何组织回复、返回空 / 报错 / 超时分别怎么办、是否可重试。
- Few-shot：正常调用、需要二选一工具、缺参数先追问、工具返回空各一条。

**典型坑**
- 只描述工具不描述“何时不用”→ 误调用。
- 允许模型臆造参数 → 明确“参数值只能来自用户输入或工具返回”。
- 没写工具失败分支 → 报错时模型自由发挥。

## 6. Agent 系统提示词
**任务特征**：一个要自主理解任务、规划、调度多个子能力 / 子 Agent、管理上下文的智能体（总控型提示词）。

**必备要素**
- **角色定位与唯一职责**：它是总控还是专职模块；总控负责理解、拆解、路由、整合，不亲自做各专职模块的活。
- **能力边界表**：能做 / 不能做两列；不能做的事明确“转给谁 / 走什么兜底”。
- **任务拆解与路由规则**：把请求映射到子能力的判别表；路由要有置信度阈值与低于阈值时的澄清 / 转人工规则。
- **上下文管理**：向子能力传递什么（已确认信息、历史结论），结果如何整合，跨轮继承哪些槽位。
- **技能模块化**：每个子能力按本手册对应类型单独写，主提示词只保留调度与整合逻辑。
- **约束层**：合规红线、事实来源（哪些必须走实时查询 / 检索，不许用记忆）、转人工 / 升级规则。
- **版本记录**：每次修改留版本号、日期、改了什么、评测结果（迭代用）。

**典型坑**
- 总控既路由又亲自答专业问题 → 职责混乱；坚持“能做 / 不能做”边界。
- 事实性内容让模型凭记忆答 → 规定必须走检索 / 工具并标注来源，未命中就如实说明。
- 一上来就拆成一堆子提示词 → 先按下面拆分原则判断是否真需要拆。

## 7. 提示词拆分原则

**默认：一个提示词能解决就不拆。** 只有出现以下任一情况才拆：
1. 一次对话要处理 2 个及以上相互独立的目标 / 产品，且策略不同；
2. 流程超过约 10 轮才能达成目标、单提示词已难以承载；
3. 存在多个完全独立的场景（如售前咨询与售后服务），规则几乎不共享。

**拆分后的结构**
```
全局提示词
├── 角色设定（全流程统一）
├── 核心目标（总体）
├── 通用约束（宪法原则、合规红线）
└── 共享信息（用户基本信息、已确认事实）

子提示词 1（某阶段）
├── 本阶段目标
├── 本阶段策略 / 技能模块
├── 入口条件（什么情况进入本阶段）
└── 出口条件 → 满足什么跳到子提示词 2 / 结束
子提示词 2 …
```

**跳转条件必须明确、可判定**，只能基于三类信号：用户明确表达（“我想了解价格”）、对话状态（必填信息已收集齐）、明确触发词（“转人工”）。模糊的跳转条件会导致模型在错误时机切到错误阶段。每个子阶段都要写清入口与出口，不允许只进不出。
