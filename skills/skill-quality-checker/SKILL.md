# Skill 质量检测 Skill

## 简介

**干什么的**：用大厂标准系统化审计一个 Skill 的质量——从能不能被清晰调用，到输入输出是否规范，到异常兜底是否完备，到方法论是否准确还原，逐项打分、定位问题、给出可执行的改进方案。

**核心方法论**：8 维度审计框架 + 5 级评分标准 + 红线一票否决 + 改进优先级排序。

**你能得到什么**：Skill 质量评分报告（总分 + 各维度得分）、问题清单（按严重程度分级）、改进建议（含具体修改方案）、与标杆 Skill 的差距分析。

**文件结构**：
```
skill-quality-checker/
├── SKILL.md                          # 主文档
└── references/
    ├── audit-checklist.md            # 8 维度逐项检查清单
    └── scorecard-template.md         # 评分卡模板
```

## 触发场景

- 写完一个 Skill，想检查质量是否达标
- 接手别人的 Skill，想快速评估好坏
- 想把 Skill 作为作品集展示，需要专业审计
- 对比多个 Skill 的质量水平
- 检查 Skill 是否符合 Codex / Claude Skill 官方规范

## 输入要求

**必需信息**：
- 待审计的 Skill（SKILL.md 文件路径或内容）

**可选补充信息**：
- 原始方法论文档（用于检查还原度）
- 对标规范版本（如 Codex skill-creator 规范）
- 审计侧重点（如只查规范符合度、只查方法论还原度）
- 实跑测试结果（如有）

**信息不全时的追问话术**：
- 缺 Skill 文件："请提供要审计的 SKILL.md 文件路径或内容。"
- 有原始方法论："如果这个 Skill 是基于某份方法论文档做的，请一并提供，我会检查方法论还原度。"
- 无特殊侧重："我会按 8 个维度全面审计，包括可调用性、输入输出规范、异常兜底、工作流完整性、单一职责、方法论还原度、规范符合度和可执行性。"

## 工作流（5 步）

### Step 1：读取与结构解析

- 读取 SKILL.md 全文及 references/ 目录下所有文件
- 解析 frontmatter（name、description、其他字段）
- 识别工作流步骤数、输入要求、输出模板、参考文件索引
- 检查文件结构完整性

**检查点**：
- frontmatter 是否只有 name 和 description（Codex 规范）
- description 是否包含触发词和能力描述
- references/ 中的文件是否都在 SKILL.md 中索引
- 是否有冗余文件（未被引用的文件）

### Step 2：8 维度逐项审计

对每个维度按 0-5 分评分，具体检查项见 `references/audit-checklist.md`：

| 维度 | 权重 | 核心检查点 |
|------|------|-----------|
| **D1 可调用性** | 15% | 触发词是否明确无歧义？description 是否说清"干什么+什么时候用"？用户说相关词时能否命中？ |
| **D2 输入规范** | 10% | 是否定义了必需信息和可选信息？信息不全时是否有追问话术？输入格式是否明确？ |
| **D3 输出规范** | 10% | 是否有明确的输出物定义？是否有模板？输出格式是否可预期？ |
| **D4 异常兜底** | 15% | 是否有异常情况处理表？信息不全/执行失败/数据缺失时怎么办？是否有降级方案？ |
| **D5 工作流完整性** | 15% | 步骤是否可执行（不是空话）？每步是否有明确产出？步骤间是否有逻辑递进？是否有检查点？ |
| **D6 单一职责** | 10% | Skill 是否只干一件事？是否有多个不相关功能塞在一起？触发场景是否聚焦？ |
| **D7 方法论还原度** | 15% | 如基于方法论，核心概念/步骤/框架是否与原文一致？有无遗漏关键步骤？有无篡改定义？ |
| **D8 规范符合度** | 10% | frontmatter 是否合规？SKILL.md 长度是否合理？是否使用 progressive disclosure？文件命名是否规范？ |

### Step 3：红线检查（一票否决项）

以下问题不参与评分，直接标记为 **P0 必须修复**：

| 红线 | 说明 |
|------|------|
| 无触发条件 | 用户不知道什么时候该用这个 Skill |
| 无工作流 | 只有方法论描述，没有可执行步骤 |
| 多职责混杂 | 一个 Skill 干 3 件以上不相关的事 |
| 方法论核心错误 | 关键概念被篡改或遗漏（如把四维可行性写成三维） |
| 编造数据/来源 | Skill 中包含虚假数据或无来源的外部信息 |
| 无输出定义 | 用户不知道用了这个 Skill 能得到什么 |

### Step 4：实跑验证（如条件允许）

- 用一个真实案例按 Skill 工作流跑一遍
- 检查工作流是否可执行（步骤是否清晰到能照做）
- 检查模板是否可直接套用
- 检查异常兜底是否真的能兜住
- 记录实跑中发现的问题

### Step 5：输出审计报告

按 `references/scorecard-template.md` 输出，包含：
1. **总分与等级**（S/A/B/C/D）
2. **8 维度评分表**（得分 + 具体问题）
3. **红线问题清单**（P0，必须修复）
4. **改进建议清单**（P1/P2，含具体修改方案）
5. **标杆对比**（与高分 Skill 的差距）
6. **修复优先级排序**（按影响面排序）

## 评分标准

| 分数 | 含义 | 标准 |
|------|------|------|
| 5 | 优秀 | 完全达标，可作为标杆，有超出预期的设计 |
| 4 | 良好 | 达标，有小瑕疵但不影响使用 |
| 3 | 及格 | 基本可用，但有明显缺失需要补充 |
| 2 | 不及格 | 关键要素缺失，无法可靠使用 |
| 1 | 严重缺陷 | 几乎不可用，需要重写 |
| 0 | 完全缺失 | 该维度内容完全没有 |

**等级划分**：
- S：≥ 4.5，无 P0 问题
- A：≥ 4.0，无 P0 问题
- B：≥ 3.0
- C：≥ 2.0
- D：< 2.0 或有 P0 红线问题

## 质量红线

1. **审计必须基于事实**：每个扣分点必须引用 SKILL.md 原文，不允许凭印象评判。
2. **改进建议必须可执行**：不能只说"需要补充异常兜底"，要说"在 XX 位置添加 XX 异常的处理方式：XX"。
3. **方法论还原度检查必须对照原文**：没有原始方法论时，该维度标注"无法评估"而非扣分。
4. **不编造规范**：引用 Codex/Claude 规范时必须基于实际规范文档，不凭记忆编造规则。
5. **评分必须一致**：相同问题在不同 Skill 中扣相同分数，审计者需说明评分理由。

## 异常兜底

| 异常情况 | 处理方式 |
|---------|---------|
| Skill 文件不存在或无法读取 | 提示用户提供正确路径，不猜测内容 |
| Skill 不是标准格式（无 frontmatter） | 先标记格式问题，再按内容尽力审计，报告中标注"非标准格式" |
| references 文件缺失 | 在 D8 规范符合度中扣分，不影响其他维度评分 |
| 没有原始方法论文档 | D7 方法论还原度标注"无法评估——未提供原始方法论"，不扣分 |
| Skill 内容过长（>500 行） | 在 D8 中建议拆分，检查是否违反 progressive disclosure |
| 批量审计多个 Skill | 逐个审计后输出横向对比表，按总分排序 |
