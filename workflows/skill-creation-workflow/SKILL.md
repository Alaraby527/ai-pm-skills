# Skill 创建 Workflow：先定标准，再写内容

## 核心原则

不要把“先写一个 Skill，再交给审核”当成默认流程。质量标准应当是 Skill 的设计输入、验收条件和发布门槛；审核 Skill 主要用于发现遗漏、验证现有 Skill 和做回归检查。

## 创建前质量合同

在编写正文前，先明确以下内容：

1. **职责边界**：解决什么问题，不解决什么问题；只保留一个清晰的核心职责。
2. **触发条件**：用户会用什么自然语言请求它；哪些相似请求应路由到其他 Skill。
3. **输入契约**：必须信息、可选信息、缺失信息的处理方式，以及需要用户补充的内容。
4. **输出契约**：输出结构、格式、颗粒度、示例和完成标准。
5. **方法论依据**：采用哪些方法、为什么适用、每一步如何落地。
6. **失败与异常**：信息不足、数据冲突、工具失败、风险场景和不适用场景如何处理。
7. **质量门槛**：如何判断结果合格，哪些问题属于发布阻断项。

## 标准创建流程

| 阶段 | 产出 | 发布前检查 |
|---|---|---|
| 1. 定义任务 | 一句话职责、适用/不适用边界 | 是否单一职责、是否与现有 Skill 重叠 |
| 2. 编写契约 | 触发条件、输入、输出、限制 | 是否能被用户和 Agent 清楚调用 |
| 3. 设计方法 | 分步骤工作流、决策规则、模板 | 是否能从输入稳定推导到输出 |
| 4. 设计防错 | 缺失输入、异常、风险、兜底 | 是否明确拒答、追问、降级和人工确认 |
| 5. 编写示例 | 正例、边界例、失败例 | 是否覆盖真实请求而不是只有理想样例 |
| 6. 预检与试跑 | 自检报告、测试记录、修订项 | 是否通过质量门槛后才进入正式审计 |
| 7. 发布与回归 | `SKILL.md`、references、版本记录 | 修改后是否重新验证触发和输出 |

## 推荐的 SKILL.md 结构

```text
---
name: skill-name
description: 触发条件 + 能力边界 + 主要产出
---

# Skill 名称

## 适用场景
## 不适用场景
## 输入要求
## 输出要求
## 工作流
## 决策规则
## 异常与风险兜底
## 质量检查清单
## 示例
```

## 与 Skill 质量检测的关系

- **创建前**：把本 Workflow 当作设计规范和预检清单，质量标准先进入 Skill 结构。
- **创建中**：用小样本正例、边界例和失败例试跑，发现问题后立即修订。
- **发布前**：再调用 `skill-quality-checker` 做独立审计和评分。
- **发布后**：任何修改都做回归测试，避免触发条件、输出格式或异常处理退化。

审核不是用来把一个“烂 Skill”补救成合格品，而是用来验证它是否满足事先定义的质量合同。

## 最低发布门槛

- [ ] 职责单一，适用和不适用边界清楚
- [ ] 触发条件具体，能与相邻 Skill 区分
- [ ] 输入、输出和缺失信息处理方式明确
- [ ] 工作流有步骤、有判断规则、有可执行产出
- [ ] 至少包含正例、边界例和失败/异常处理
- [ ] 不编造事实；不确定内容有标注和追问机制
- [ ] 通过创建前预检后，才进入独立质量审计
